## Context

ClawHub 当前已经具备本地用户、外部身份映射、JWT Session、邮箱登录和多 provider OAuth 登录能力，但现有语义仍然偏向“邮箱注册/登录”和“第三方首次登录建号”。产品现在确认采用“飞书主登录、邮箱辅助登录”的最终方案，因此需要把认证入口和本地账号主体彻底分离：

- 飞书身份和邮箱身份都只是登录或绑定入口
- 平台唯一账号主体始终是本地用户 `users.id`
- 业务数据、权限、资料全部绑定在本地用户上

这一变更是跨后端认证层、前端登录页/设置页、用户数据模型和管理权限规则的横切变更，并且直接影响未来的管理用户准入，因此需要在编码前先固化技术设计。

现有约束包括：

- 不能破坏现有 `clawhub_session` Cookie 会话模型
- 不能破坏现有 `/api/v1/users/me`、CLI Token 和管理端权限协议
- 不允许按邮箱自动把飞书身份和现有邮箱身份合并
- 未绑定邮箱的飞书用户不能拥有管理权限

## Goals / Non-Goals

**Goals:**

- 引入飞书 H5 主登录能力，并复用现有本地 Session
- 引入普通浏览器中的飞书 OAuth 登录能力，并复用现有本地 Session
- 把邮箱链路重新定义为兼容登录和邮箱绑定能力
- 明确“飞书身份 / 邮箱身份 -> 本地用户”的统一账号模型
- 明确管理权限必须依附“本地用户 + 已绑定邮箱”
- 为后续实现提供清晰的接口、状态和数据模型边界

**Non-Goals:**

- 本次不直接实现代码
- 不引入飞书组织架构同步或基于组织自动授予角色
- 不把飞书 Access Token 作为平台会话
- 不通过邮箱字段做自动账号合并
- 不改造 CLI 为直接感知飞书 OAuth
- 不把“飞书工作台唤起浏览器进入应用”作为本期必须交付能力

## Decisions

### 决策一：平台唯一账号主体是本地用户 `users.id`

选择：

- 统一以本地用户作为唯一账号主体
- 飞书身份和邮箱身份都只是绑定到本地用户的登录身份

原因：

- 这能避免“飞书账号”和“邮箱账号”被实现成两套平行主体
- 也能确保技能、权限、资料不会因登录方式切换而分裂

备选方案：

- 让飞书和邮箱分别成为两套主体，再通过业务层做合并

不采用原因：

- 风险高，容易造成重复账号、权限漂移和数据归属不清

### 决策二：飞书为主登录，邮箱为辅助登录与绑定能力

选择：

- 飞书客户端内优先通过 `requestAccess` 登录
- 普通浏览器支持飞书 OAuth 重定向登录
- 浏览器 OAuth 跳转通过独立认证导航基地址发起，不与 API 代理混用
- 邮箱继续保留为兼容登录与绑定能力
- 邮箱注册 / 激活 / 登录链路重新定义为绑定邮箱、验证邮箱、进入已有本地用户

补充边界：

- 飞书客户端内免登和普通浏览器飞书 OAuth 登录是两条并存的主登录链路
- 飞书工作台唤起浏览器进入应用属于后续可选增强，不纳入本期主流程

原因：

- 符合当前产品方向
- 能兼容历史邮箱用户
- 能保留管理员与历史邮箱用户的兼容进入方式

备选方案：

- 完全移除邮箱链路

不采用原因：

- 与“管理权限必须依附已绑定邮箱”相冲突
- 也会破坏历史邮箱用户的兼容性

### 决策三：不按邮箱自动合并账号

选择：

- 飞书首次登录未命中身份映射时，默认创建新的本地用户
- 只有用户主动绑定，才把飞书身份和邮箱身份收敛到同一个本地用户

原因：

- 邮箱不是强身份主键
- 自动合并会引入误绑、越权和账号劫持风险

备选方案：

- 通过邮箱自动把飞书用户合并到已有邮箱用户

不采用原因：

- 安全边界过弱，且不符合当前需求文档中的硬约束

### 决策四：管理权限授予必须依赖邮箱绑定状态

选择：

- 增加显式的邮箱绑定状态，例如 `has_bound_email`
- 任何 `admin`、`moderator`、`isSuperuser` 判定都必须先通过邮箱绑定校验

原因：

- 产品已经明确“未绑定邮箱的飞书账号不具备管理权限”
- 需要把这条业务规则落为后端可审计、可实现的前置校验

备选方案：

- 继续只看 `role` 或 `isSuperuser`，不关心邮箱绑定状态

不采用原因：

- 会直接违反产品约束

### 决策五：邮箱链路在实现上要区分“绑定”与“登录”

选择：

- `POST /auth/login`：作为邮箱辅助登录，进入已有本地用户
- `POST /auth/register` / `POST /auth/activate`：优先解释为邮箱绑定与验证流程
- 新增或等效支持 `POST /auth/email/bind`

原因：

- 这样能让现有链路继续存在，但语义升级为统一账号模型下的辅助能力

备选方案：

- 继续保留邮箱注册/激活的“默认建号”语义

不采用原因：

- 会和飞书主登录下的单主体模型冲突

## Risks / Trade-offs

- [历史邮箱流程和新语义不一致] → 通过文案、接口语义和设置页展示统一表达“绑定邮箱/兼容登录”
- [未绑定邮箱的飞书用户可能困惑为什么不能管理] → 在前端显式提示“当前账号未完成邮箱绑定，因此不具备管理权限资格”
- [飞书身份首次登录会创建新本地用户，导致用户以为丢数据] → 必须提供清晰的“绑定飞书”入口，并避免自动合并
- [后端现有邮箱登录代码可能仍隐式承担建号语义] → 在实现时明确分离“邮箱登录进入已有用户”和“邮箱绑定到当前用户”
- [superuser 现有匹配逻辑只看配置字段] → 在权限判定中额外增加邮箱绑定前置校验，即使命中 superuser 也不能绕过该条件
- [飞书 H5 与浏览器 OAuth 被前端混成单一入口] → 在设计上明确按运行环境分流，避免普通浏览器误走飞书客户端 SDK 链路
- [飞书原始标识被直接展示到前端] → 在接口返回和 UI 展示层区分“内部标识字段”和“用户可见资料字段”，默认不向用户暴露原始标识

## Migration Plan

1. 先补齐 OpenSpec 规范，明确飞书主登录、邮箱绑定和管理权限规则
2. 在实现阶段调整后端用户与身份服务，使所有登录入口都收敛到本地用户
3. 增加普通浏览器飞书 OAuth 登录与绑定回调链路
4. 增加浏览器 OAuth 独立导航配置，避免代理层吞掉 30x 跳转
5. 引入邮箱绑定状态字段和相关校验逻辑
6. 改造前端登录页、设置页和提示文案
7. 校验管理权限入口，确保未绑定邮箱的飞书用户无法进入管理能力
8. 保留邮箱兼容登录能力，验证历史邮箱用户和管理员仍可进入原本地用户

回滚策略：

- 若飞书主登录实现异常，可临时停用飞书入口，保留现有邮箱辅助入口
- 已有本地用户和 `clawhub_session` 模型不变，因此回滚不涉及主体数据迁移

## Open Questions

- 邮箱绑定状态是直接基于现有邮箱激活状态推导，还是单独新增显式字段
- 未登录场景下是否还允许邮箱注册创建本地用户，还是完全限制为登录后绑定
- 管理端是否需要显式展示“邮箱已绑定 / 未绑定”状态
- 是否需要支持解绑飞书或解绑邮箱，以及解绑后的权限降级规则
