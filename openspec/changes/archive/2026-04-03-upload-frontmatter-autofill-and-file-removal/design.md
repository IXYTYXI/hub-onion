## Context

当前上传页已经完成从 Convex 上传链路向 Go 后端 multipart 发布接口的迁移，页面本身维护了完整的本地待发布状态，包括 `files`、`slug`、`displayName`、`version`、`tags` 和实时校验结果。文件夹、拖拽、zip / tar.gz / gz 展开也都已经统一收敛为前端的 `File[]` 数据结构。

本次变更的两个目标都发生在“真正调用发布接口之前”：

- 从 `SKILL.md` frontmatter 自动补全名称相关字段
- 允许用户直接删除文件列表中的单个文件

因此它们都属于上传页前端本地状态编辑能力，而不是后端协议问题。约束也很明确：

- 不能重新耦合旧 `convex/` 目录
- 不能改变现有 `/api/v1/skills` multipart 请求结构
- 必须保持用户手工输入高于自动填充

相关方主要包括：

- 发布 skill 的终端用户
- 维护上传页和共享前端工具的开发者
- 依赖现有发布协议的 Go 后端与 CLI 兼容性链路

## Goals / Non-Goals

**Goals:**

- 在上传页本地识别 `SKILL.md` / `skills.md` 并解析 frontmatter `name`
- 在不覆盖用户手工输入的前提下，为 `slug` 和 `displayName` 提供默认值自动填充
- 在文件列表中增加逐行删除能力
- 删除文件后复用现有派生状态模型完成即时校验重算
- 将 frontmatter 解析逻辑放到新的前端共享位置，避免继续从 `convex/` 目录引用
- 保持发布接口、后端处理和响应格式不变

**Non-Goals:**

- 不让后端二次解析 `SKILL.md` 来推导或校验 `displayName`
- 不增加新的发布字段或新的上传协议
- 不处理多个 skill 候选包选择问题
- 不引入批量删除、撤销删除或复杂文件编辑器
- 不把自动解析扩展到 `description`、`metadata` 或 changelog 自动生成

## Decisions

### 决策 1：frontmatter 解析逻辑迁移到新的前端共享模块

将所需解析能力放到新的 `src/lib/skillFrontmatter.ts`，只提供上传页当前真正需要的最小能力：

- 解析 markdown 顶部 frontmatter
- 读取 `name`
- 根据 `name` 生成推荐 slug / displayName
- 辅助定位主 `SKILL.md`

原因：

- 当前旧实现位于 `convex/lib/skills.ts`，虽然是纯函数，但继续引用会污染迁移边界
- 这类逻辑未来也可能被 `/import` 等前端入口复用，放在 `src/lib/` 更合理

备选方案：

- 继续直接复用 `convex/lib/skills.ts`
  - 放弃原因：边界不清晰，后续删除旧代码成本更高
- 把逻辑提到 `packages/schema`
  - 放弃原因：当前需求只在前端上传页使用，过早上提会扩大改动范围

### 决策 2：自动填充只作用于“空值且未被手工修改”的字段

上传页将新增轻量的手工编辑标记，例如：

- `slugTouched`
- `displayNameTouched`

自动解析成功后，只有在字段为空且对应标记为未触达时才写入默认值。

原因：

- 用户输入必须高于系统猜测
- 重新上传目录或删除文件后，若系统回写已确认字段，会造成明显的交互回退

备选方案：

- 每次文件变化都强制用 `SKILL.md` 覆盖字段
  - 放弃原因：会破坏用户已确认输入
- 只根据当前字段是否为空判断，不记录 touched 状态
  - 放弃原因：用户可能先输入再清空，此时难以区分是否允许再次自动填充，行为不稳定

### 决策 3：自动解析挂在 `applyExpandedFiles()` 链路中统一执行

所有文件来源最终都会经过 `applyExpandedFiles(selected)`：

- 目录选择
- 拖拽文件夹
- 压缩包展开

本次将自动解析也挂在这条统一链路中，在 `expandFilesWithReport()` 完成后立即尝试读取 `SKILL.md`。

原因：

- 可以保证所有上传入口行为一致
- 不需要为不同入口写多套副作用逻辑

备选方案：

- 用单独 `useEffect` 监听 `files` 再解析
  - 放弃原因：需要额外处理时序和重复触发，调试成本更高

### 决策 4：文件删除直接操作 `files` 状态，依赖现有派生状态自动重算

当前上传页的以下数据都已经是基于 `files` 推导：

- `totalBytes`
- `normalizedPaths`
- `hasRequiredFile`
- `validation`

因此删除交互不新增独立“重算器”，只需要：

- 在文件列表渲染时保留 index
- 删除时按 index 从 `files` 中移除对应项

原因：

- 现有状态模型已经足够，继续增加中间状态只会提高复杂度
- 按 index 删除与当前显示行一一对应，行为最稳

备选方案：

- 按路径删除
  - 放弃原因：同名路径或路径规范化后可能出现歧义
- 建立单独的可编辑文件 ViewModel
  - 放弃原因：对当前需求过重

### 决策 5：删除 `SKILL.md` 后保留已填字段，只通过校验阻止发布

当用户删除 `SKILL.md` 时：

- 不自动清空 `slug` / `displayName`
- 依赖现有校验逻辑立即提示缺失必需文件
- 发布按钮变为禁用

原因：

- 字段值可能已经被用户继续修改，不应因为删文件而丢失
- 校验提示已经足够表达“当前不能发布”

备选方案：

- 删除 `SKILL.md` 时同步清空字段
  - 放弃原因：会带来非预期的数据丢失感

## Risks / Trade-offs

- [frontmatter 解析逻辑与旧实现出现细微差异] → 复用同样的 YAML 解析策略，并为解析工具增加独立测试
- [自动填充逻辑覆盖用户已确认输入] → 使用 touched 标记而非单纯依赖字段是否为空
- [删除行为与当前列表显示不一致] → 删除逻辑按当前渲染 index 执行，避免路径匹配歧义
- [解析失败影响主流程] → 将解析错误降级为静默失败，不影响文件展示与手工填写
- [后续其他页面也需要该能力时产生重复实现] → 先放在 `src/lib/skillFrontmatter.ts`，保持函数边界清晰，后续如有需要再上提到共享包

## Migration Plan

本次变更为纯前端本地行为增强，不涉及数据库或 API 迁移。

推荐实施顺序：

1. 新增 `src/lib/skillFrontmatter.ts`
2. 在上传页接入 `SKILL.md` 自动解析和 touched 状态
3. 在文件列表中增加删除按钮
4. 调整少量文案与样式
5. 补充上传页测试和解析工具测试

回滚策略：

- 若自动填充行为出现异常，可先移除上传页中的自动解析调用，保留删除交互
- 若删除交互出现问题，可仅回退文件列表按钮渲染和对应状态更新逻辑
- 因未改后端协议，回滚不涉及数据兼容问题

## Open Questions

- `displayName` 是否应直接使用原始 `name`，还是统一经过标题化处理后填入，当前建议以更接近用户可读名称的形式填充
- 当用户手工输入后又清空字段时，是否重新允许自动填充，当前建议实现为可重新自动填充，但需要在编码阶段统一规则
- 对于同一个上传包中存在多个 `SKILL.md` 候选时，是否仅按稳定优先级取第一个即可，当前设计按最小实现处理，不新增候选选择器
