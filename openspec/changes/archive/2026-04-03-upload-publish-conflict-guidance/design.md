## Context

当前上传页已经具备本地文件校验和 multipart 发布能力，但在 `slug` 已存在、同一用户应发布新版本、或版本号重复时，页面仍可能只向用户展示通用失败提示。与此同时，Go 后端 publish handler 会把“他人占用 slug”和“重复版本”这类可恢复冲突统一落成 `500 Internal Server Error`，导致用户无法判断下一步该修改 `slug`、修改 `version`，还是按“发布新版本”继续操作。

当前系统已有一部分可复用基础：

- 前端已能通过现有查询接口获取 skill 详情和版本列表
- 上传页本身已维护完整表单状态和提交按钮状态
- 后端当前已能识别“owner 冲突”和“重复版本”，只是没有用稳定语义返回

本次变更涉及前端上传页交互和后端发布错误语义两个层面，因此属于一次跨前后端的收口型变更。

## Goals / Non-Goals

**Goals:**

- 在上传页输入 `slug` 后，识别该 `slug` 是可新建、属于当前用户、还是已被他人占用
- 当 `slug` 属于当前用户时，将页面语义切换为“发布新版本”，并展示当前最新版本
- 当 `slug` 被他人占用时，明确阻止继续发布并提示更换 `slug`
- 当当前用户提交重复版本号时，提示升级版本号，而不是展示通用服务端错误
- 让后端对已知业务冲突返回稳定冲突状态，供前端做可靠映射

**Non-Goals:**

- 不引入新的发布协议或新的复杂预检查接口
- 不在本次变更中重构整个上传页布局
- 不处理技能所有权转移、协作者发布等更复杂权限模型
- 不扩展到 import 页面或 CLI 之外的其他创建入口

## Decisions

### 决策 1：前端优先复用现有详情与版本接口做预检查

上传页的 `slug` 预检查优先复用现有能力：

- `GET /api/v1/skills/:slug` 判断 skill 是否存在以及 owner 信息
- `GET /api/v1/skills/:slug/versions` 获取当前版本列表或最新版本

原因：

- 现有接口已经能满足“新建 / 新版本 / 被占用”的首轮判断
- 可以避免在本次变更里立即引入新的预检查协议

备选方案：

- 新增专门的 `POST /api/v1/skills/check-slug` 或类似接口
  - 放弃原因：虽然长期更清晰，但会扩大本次协议改动范围

### 决策 2：上传页维护一个轻量的发布意图状态

前端增加统一状态，例如：

- `available`
- `owned`
- `taken`
- `error`

该状态只用于页面语义切换和按钮可用性判断，不参与最终发布协议。

原因：

- “我是在新建还是在发新版本”是上传页当前缺失的核心心智
- 若不把这个状态显式建模，页面只能不断用零散文案做补丁式判断

### 决策 3：提交前检查只作引导，提交后仍以后端结果为准

即使上传页预检查显示“可新建”或“可发新版本”，最终仍必须以后端发布返回为真相。

原因：

- 用户停留在页面期间，服务端状态可能变化
- 权限和唯一性最终仍只能由后端保证

备选方案：

- 让预检查结果直接决定是否完全跳过后端冲突处理
  - 放弃原因：会引入竞态，造成错误判断

### 决策 4：后端必须把已知业务冲突从 500 中分离出来

本次建议后端至少稳定区分：

- `slug` 已被他人占用
- 当前用户重复发布已存在版本
- 其他真实服务端异常

推荐语义：

- `403 not_owner` 或等价错误
- `409 version_exists`
- `500 internal_error`

原因：

- 前端若长期依赖错误文本匹配，不稳定且难维护
- 业务冲突与内部错误在产品语义上必须分开

### 决策 5：前端增加错误翻译层作为过渡兜底

在后端稳定语义完全到位前，前端仍增加一层错误映射：

- `permission denied: skill owned by another user` → 更换 `slug`
- `version already exists` → 升级 `version`

原因：

- 可以立即改善用户体验
- 与最终的错误码方案不冲突，后续只需替换映射来源

## Risks / Trade-offs

- [预检查与提交时真实状态不一致] → 提交前检查只作引导，提交后仍以后端结果为真相
- [前端依赖错误文本做兜底映射不稳定] → 仅作为过渡方案，后续切换到稳定错误码
- [复用现有详情接口时 owner 信息不足] → 若现有详情返回不足以区分归属，需要后端先补齐必要字段
- [上传页状态变多导致表单逻辑变复杂] → 将发布意图收敛为单一状态枚举，而不是在多个字段上散落判断

## Migration Plan

建议按两阶段推进：

1. 前端先接入 `slug` 预检查、页面语义切换和提交失败文案翻译
2. 后端补充稳定业务错误语义，替换前端对错误文本的依赖

回滚策略：

- 若预检查带来误导，可仅回退提交前提示，保留提交后错误翻译
- 若后端错误语义改动引发兼容问题，可临时恢复文本级兜底

## Open Questions

- 现有 `GET /api/v1/skills/:slug` 返回的 owner 信息是否足以让上传页准确判断“是不是我自己的 skill”
- 版本区域是只展示“当前最新版本”，还是同时给出建议的下一个 semver
- 发布按钮是否需要在 `owned` 状态下直接改文案为“发布新版本”，还是只保留辅助提示即可
