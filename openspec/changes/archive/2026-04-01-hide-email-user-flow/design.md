## Context

当前 ClawHub 已经以飞书作为主登录方向，但前端主路径仍混合暴露邮箱辅助登录、邮箱权限说明和用户审核入口，导致用户可见体验与产品方向不一致。现有后端已经同时承载邮箱链路、飞书链路、审核状态机和管理接口，因此本次不适合直接删除后端能力，而应先从前端可见性与最小登录状态策略入手收口。

本次变更横跨前端登录页、管理后台、设置页、前端文案与测试，同时需要对飞书新用户的登录状态做最小兜底调整。这是一个跨模块但低侵入的收口型改动，适合先通过 OpenSpec 明确边界后实施。

## Goals / Non-Goals

**Goals:**

- 让登录页只暴露飞书登录入口
- 让管理后台前端彻底退出用户审核主流程
- 让设置页不再公开表达邮箱资格与管理权限之间的关系
- 让普通用户在飞书主登录链路中不感知待审核状态
- 保持后端邮箱接口、审核接口和数据库结构兼容保留

**Non-Goals:**

- 不删除邮箱注册、激活、登录相关接口
- 不删除用户审核接口
- 不重构 `HasManagementAccess`、`IsSuperuser` 或完整权限模型
- 不处理存量用户状态修复
- 不调整 CLI 协议和 CLI 登录流程

## Decisions

### 决策一：采用“前端收口 + 后端兼容保留”而不是立即删除能力

选择：

- 前端隐藏邮箱辅助登录、隐藏用户审核入口、统一权限提示
- 后端继续保留邮箱与审核接口，作为兼容层

原因：

- 当前需求明确要求先去掉可见性，而不是完整移除邮箱体系
- 直接删除后端能力会扩大范围，牵动接口、数据库和更多测试
- 先收口可见性可以快速对齐产品方向，并为后续重构留出余地

备选方案：

- 直接删除 `/auth/register`、`/auth/activate`、`/auth/login` 与审核接口

不采用原因：

- 范围明显过大，与当前阶段目标不匹配
- 会引入更多回归风险和迁移工作

### 决策二：管理后台整块移除用户审核前端入口，而不是只隐藏按钮

选择：

- 前端不再请求 `/api/v1/admin/users*`
- 移除 `Users` tab、用户列表、用户详情和审核动作
- Management 页面默认收敛为 skill 管理场景

原因：

- 只隐藏按钮但继续加载用户审核数据，会留下半隐藏状态
- 用户审核逻辑当前集中在一个页面中，适合整块退出前端主路径
- 彻底停止请求审核接口更符合“去可见性”的产品目标

备选方案：

- 保留 `Users` tab，只隐藏 approve/reject 等按钮

不采用原因：

- 页面仍然显性暴露审核语义
- 仍会请求审核接口，不能满足需求边界

### 决策三：通过飞书新用户默认可登录，避免普通用户感知审核流

选择：

- 保持飞书授权创建的新用户直接进入可登录状态
- 不要求本次处理存量用户

原因：

- 需求明确不考虑存量用户
- 普通用户对审核流的感知主要来自登录错误提示
- 只要新飞书用户不进入 `review_pending`，前端就不需要再为此维持一整套显性提示

备选方案：

- 继续允许飞书新用户进入 `review_pending`，仅通过文案弱化提示

不采用原因：

- 用户仍然会感知审核流存在
- 与“普通用户不显性暴露审核流”的目标冲突

### 决策四：设置页保留账号信息与飞书绑定状态，但移除邮箱资格叙事

选择：

- 保留基础资料、飞书绑定状态、API Token 管理
- 去掉邮箱绑定与管理权限之间的公开说明

原因：

- 设置页仍需承载账号信息和 Token 管理
- 本次要收起的是“邮箱资格叙事”，不是把设置页做成纯空页面

备选方案：

- 完全删除所有邮箱相关展示字段

不采用原因：

- 当前需求没有要求清空所有邮箱字段
- 这会把“可见性收口”扩展成“数据呈现重构”

## Risks / Trade-offs

- [前端隐藏但后端保留] → 在研发认知和文档中明确这是兼容层，不作为本次失败判定
- [管理后台定位变化] → 同步调整标题、副标题和默认视图，使其更像 skill 管理后台
- [权限原因变得不透明] → 前端统一使用无权限提示，调试时依靠后端日志与接口响应定位真实原因
- [飞书新用户策略与既有审核模型并存] → 本次只要求保证新飞书用户主链路可登录，不扩展到完整审核模型重构
