## 新增需求

### 需求：流式 Multipart 解析
系统应流式解析 multipart/form-data 请求，避免缓冲整个请求到内存。

#### 场景：流式读取 payload
- **当** 接收 multipart 请求时
- **则** 系统应流式读取 payload 部分并解析 JSON，无需缓冲整个 payload

#### 场景：流式读取文件
- **当** 接收 multipart 文件时
- **则** 系统应获取 io.Reader 而非将文件内容加载到内存

#### 场景：内存限制
- **当** 处理包含多个大文件的请求时
- **则** 系统应保持内存使用在合理范围内（每个文件约 32KB 缓冲区）

### 需求：TeeReader 模式
系统应使用 io.TeeReader 同时执行多个操作而不重复读取数据。

#### 场景：同时上传和哈希
- **当** 处理文件上传时
- **则** 系统应使用 io.TeeReader 同时将数据流向 OSS 和 SHA-256 哈希器

#### 场景：单次遍历
- **当** 处理文件时
- **则** 系统应只遍历文件数据一次，避免先读取计算哈希再读取上传

#### 场景：实现示例
- **当** 实现流式上传时
- **则** 系统应使用如下模式：
  ```go
  hasher := sha256.New()
  teeReader := io.TeeReader(fileReader, hasher)
  // 上传 teeReader，自动同时计算哈希
  ossClient.PutObject(ctx, &s3.PutObjectInput{Body: teeReader})
  hash := hex.EncodeToString(hasher.Sum(nil))
  ```

### 需求：并发文件上传
系统应支持并发上传多个文件以提高性能。

#### 场景：并发限制
- **当** 一个 skill 包含多个文件时
- **则** 系统应使用 goroutine 并发上传，并发数限制为 5

#### 场景：信号量控制
- **当** 实现并发上传时
- **则** 系统应使用 channel 作为信号量控制并发数

#### 场景：错误聚合
- **当** 并发上传多个文件时
- **则** 系统应收集所有错误，如果任一上传失败则清理所有已上传文件

#### 场景：WaitGroup 同步
- **当** 并发上传时
- **则** 系统应使用 sync.WaitGroup 等待所有上传完成

### 需求：内存效率验证
系统应验证流式处理确实减少了内存使用。

#### 场景：50MB 文件上传
- **当** 上传 50MB 文件时
- **则** 系统峰值内存使用应约为 32KB（缓冲区大小），而非 50MB

#### 场景：并发上传内存
- **当** 并发上传 5 个文件时
- **则** 系统峰值内存使用应约为 160KB（5 × 32KB），而非文件总大小

#### 场景：内存监控
- **当** 运行集成测试时
- **则** 应监控内存使用以验证流式处理的效果

### 需求：错误处理和清理
系统应在上传失败时正确清理已上传的文件。

#### 场景：部分上传失败
- **当** 多个文件中有一个上传失败时
- **则** 系统应删除所有已成功上传到 OSS 的文件

#### 场景：清理忽略错误
- **当** 清理已上传文件时
- **则** 系统应记录删除失败但不因此失败整个操作

#### 场景：事务回滚
- **当** 上传失败导致清理时
- **则** 系统应同时回滚数据库事务

### 需求：超时和取消
系统应支持请求超时和取消。

#### 场景：上传超时
- **当** 单个文件上传超过配置的超时时间时
- **则** 系统应取消上传并返回超时错误

#### 场景：Context 传播
- **当** 处理上传请求时
- **则** 系统应将 context.Context 传递给所有 OSS 操作以支持取消

#### 场景：客户端断开
- **当** 客户端断开连接时
- **则** 系统应通过 context 取消所有进行中的上传操作

### 需求：性能优化
系统应优化流式上传性能。

#### 场景：缓冲区大小
- **当** 配置流式上传时
- **则** 系统应使用 32KB 缓冲区大小（平衡内存和性能）

#### 场景：TCP 优化
- **当** 上传到 OSS 时
- **则** 系统应复用 HTTP 连接（HTTP/1.1 keep-alive 或 HTTP/2）

#### 场景：并发优化
- **当** 上传多个小文件时
- **则** 并发上传应显著减少总时间（理想情况下接近 1/N）
