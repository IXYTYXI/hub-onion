## Context

当前 Go 后端已经具备本地邮箱注册、邮箱验证码激活、邮箱密码登录、GitHub/GitLab OAuth 登录和 JWT 会话能力，但缺少统一的准入审核层。现状中，本地邮箱用户在激活成功后会直接进入可登录状态，OAuth 用户首次登录时也会直接创建并使用本地账户，这与“只允许经过审核的用户进入系统”的要求不一致。

本次变更需要同时覆盖两条入口：
- 本地邮箱注册流：`register -> activate -> login`
- OAuth 登录流：`oauth callback -> identity upsert -> session issue`

同时，仓库已经存在 `role` 字段和部分管理/审核相关历史能力预期，但没有“本地超级用户配置”和“审核其他用户是否通过”的后端实现。需求明确要求超级用户通过配置文件指定，并支持 `user_id`、`email`、`handle` 任一字段精确匹配。

## Goals / Non-Goals

**Goals:**
- 为本地邮箱注册用户和 OAuth 用户建立统一审核状态机。
- 引入可配置的超级用户识别逻辑，用于审核和用户启停管理。
- 让只有 `active` 用户能够完成平台登录并获得会话。
- 为管理员提供最小可用的审核管理 API。
- 修正 SMTP 未配置时仍然创建待激活用户的流程缺陷。

**Non-Goals:**
- 不引入完整 RBAC 或新的常驻权限系统。
- 不处理历史已存在 `active` 用户的批量回刷审核。
- 不改变现有 OAuth Provider 集成方式本身。
- 不在本次设计中细化前端视觉或完整后台管理台交互。

## Decisions

### 1. 使用统一状态机区分“邮箱确认”和“人工审核”

决策：
- 将用户准入状态统一为 `email_pending`、`review_pending`、`active`、`rejected`、`disabled`。
- 本地邮箱注册用户先经过邮箱验证，再进入人工审核。
- OAuth 用户没有邮箱验证码步骤，首次建号后直接进入 `review_pending`。

原因：
- 邮箱真实性和业务准入是两个独立问题，拆开后状态语义清晰，错误提示也更准确。
- 该方案同时适用于本地账号和 OAuth 账号，避免形成两套准入规则。

备选方案：
- 继续使用 `pending/active/disabled` 三态。
  - 放弃原因：无法区分“未激活邮箱”和“待管理员审核”，前后端无法给出正确反馈。

### 2. 超级用户采用配置驱动的“或匹配”

决策：
- 在认证配置中新增超级用户列表。
- 每个配置项可包含 `user_id`、`email`、`handle` 任一或多个字段。
- 运行时按三类字段做精确相等匹配，任一命中即视为超级用户。

原因：
- `user_id` 最稳定，适合生产长期配置。
- `email` 便于初期引导和人工维护。
- `handle` 适合作为补充配置，满足已有使用习惯。

备选方案：
- 仅支持 `handle`。
  - 放弃原因：可变性过强，不满足稳定识别要求。
- 仅支持 `user_id`。
  - 放弃原因：初始引导阶段不够方便。

### 3. OAuth 用户复用现有身份同步，但会话签发前追加审核状态判断

决策：
- 保留现有 OAuth provider、identity upsert 和本地用户同步逻辑。
- 将“是否签发 JWT / 是否写 session cookie”放到统一的状态判断之后。
- OAuth 首次登录创建用户时默认状态为 `review_pending`。

原因：
- 这能最大限度复用当前实现，减少改动面。
- 将准入控制集中在登录完成前，邮箱登录和 OAuth 登录可以共用同一套状态门禁。

备选方案：
- 在 OAuth callback 前直接拒绝未审核用户。
  - 放弃原因：首次登录仍需要创建或同步本地身份，不适合过早中断。

### 4. 管理接口单独挂载在 `/api/v1/admin/users`

决策：
- 审核和启停用户的接口统一放在 `/api/v1/admin/users` 下。
- 普通用户资料接口仍保留在 `/api/v1/users`。

原因：
- 权限边界清晰，避免与普通用户接口混淆。
- 便于后续继续扩展后台管理能力。

备选方案：
- 继续挂载在 `/api/v1/users/*`。
  - 放弃原因：语义混杂，不利于权限审计。

### 5. SMTP 未配置时直接禁止本地邮箱注册

决策：
- 若 SMTP 配置缺失，则 `POST /auth/register` 返回错误，不创建任何新用户。

原因：
- 当前逻辑会在未发信的情况下创建待激活用户，属于错误状态积累。
- 注册成功就必须保证后续激活链路可达。

备选方案：
- 保持现状，仅记录警告日志。
  - 放弃原因：用户会被卡死在不可恢复的状态。

## Risks / Trade-offs

- [超级用户配置错误导致无人可审核] → 接受该风险，并通过部署文档和启动日志提示当前超级用户配置是否为空。
- [OAuth 用户首次登录后无法直接进入系统，可能影响现有测试或联调] → 在登录返回中显式区分“待审核”错误，前端同步增加状态提示。
- [状态迁移涉及现有 `status` 字段语义变化] → 保持历史 `active` 用户不回刷，只对新注册和新 OAuth 用户采用新状态。
- [管理员接口与未来 RBAC 方案可能重叠] → 先用超级用户配置实现最小闭环，后续如需角色体系再向正式权限系统迁移。

## Migration Plan

1. 扩展配置模型，支持超级用户列表。
2. 扩展用户状态枚举和审核审计字段。
3. 修改本地邮箱注册/激活逻辑，使其进入 `email_pending -> review_pending`。
4. 修改 OAuth 首次登录创建用户逻辑，使新用户进入 `review_pending`。
5. 在邮箱登录和 OAuth 会话签发前统一校验用户状态。
6. 新增 `/api/v1/admin/users` 审核接口和超级用户鉴权。
7. 前端补充待审核/已拒绝/已停用提示页与管理入口。

回滚策略：
- 若变更未上线，可直接回退代码与迁移。
- 若已上线且需要回滚，可保留新增字段，仅将登录门禁回退为兼容旧逻辑。

## Open Questions

- 是否要在后台管理页中加入按邮箱域名、注册方式、本地/OAuth 来源的筛选能力。
- 是否需要为超级用户提供只读的用户搜索接口，供后续 `set-role`、`ban-user` 等管理命令复用。
