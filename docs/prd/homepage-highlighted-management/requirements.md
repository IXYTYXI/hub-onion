# 首页精选技能、管理配置与安装统计收口需求文档

## 1. 文档目的

本文档用于定义 ClawHub 当前项目中“首页精选技能与热门技能展示恢复、highlighted 管理能力补齐，以及安装统计展示收口”的需求边界，作为后续技术设计、任务拆解和实施验收的依据。

本文档基于当前仓库代码现状编写，目标是为现有 Go 后端 + 前端页面提供一轮可以直接落地的补齐方案。

## 2. 背景

当前系统存在以下现状：

- 首页 `/` 已经展示“精选技能”和“热门技能”两个区块
- 但首页代码中这两个区块仍使用占位空数组，因此页面始终为空
- 前端技能列表和搜索链路仍保留 `highlighted` / “仅看精选” 的概念
- Go 后端当前没有 `highlighted` 字段、过滤逻辑或管理接口
- 管理后台 `/management` 当前只支持删除和恢复 skill，不支持精选运营
- 管理后台 `/management` 的 skill 列表作者栏当前仍可能展示 UID，无法满足后台运营识别作者的需要
- 公开用户页 `/u/:handle` 的用户信息区域当前也仍可能展示 UID 风格 handle，而不是飞书邮箱
- 详情页仍展示“当前安装 / 累计安装”双指标
- Go 后端存在 `stats_installs` 字段，但当前没有写入逻辑
- CLI 安装流程通过下载接口完成，因此用户已安装 skill，但页面安装统计仍显示为 0

这会导致产品层面出现明显不一致：

- 首页存在精选展示位，但没有真实数据来源
- 列表页存在精选筛选，但后端不支持
- 管理后台承担 skill 管理角色，但缺少精选配置能力
- 用户实际已经完成安装，但详情页仍显示虚假的 0 安装统计

## 3. 核心目标

本次需求的核心目标如下：

1. 恢复首页“精选技能”和“热门技能”的真实数据展示
2. 为 skill 建立可持久化的 `highlighted` 状态
3. 在管理后台提供设置和取消 `highlighted` 的操作入口
4. 让前端列表页和首页都能复用同一套 `highlighted` 数据能力
5. 以最小实现让 CLI 安装能够同步累计 `stats_installs`
6. 收起当前不可信的“当前安装”展示，只保留可落地的累计安装展示
7. 将管理后台 skill 列表中的作者展示统一收口为已获取的飞书授权邮箱
8. 将公开用户页中的用户信息展示统一收口为飞书邮箱优先
9. 形成“数据库字段 -> 后端接口 -> 管理后台 -> 首页展示”的完整闭环

## 4. 范围

### 4.1 本次必须覆盖

- 数据库为 `skills` 增加可持久化的 `highlighted` 状态字段
- 后端 `GET /api/v1/skills` 支持按 `highlighted` 过滤
- 后端管理接口支持设置和取消 skill 的 `highlighted`
- 管理后台 `/management` 展示当前 skill 的精选状态，并提供切换操作
- 管理后台 `/management` 的 skill 列表作者栏展示飞书授权邮箱，而不是 UID
- 公开用户页 `/u/:handle` 的用户信息中优先展示飞书邮箱，而不是 UID 风格 handle
- 首页“精选技能”基于 `highlighted` 状态读取真实数据
- 首页“热门技能”基于真实技能数据读取，不再使用占位空数组
- 管理列表接口与详情接口返回 `highlighted` 状态，供前端渲染
- 后端在下载成功时同步累计 `stats_installs`
- 详情页先只展示“累计安装”，不再展示“当前安装”
- 前端详情接口消费的安装数字应与后端 `stats_installs` 保持一致

### 4.2 本次建议覆盖

- 技能列表页现有“仅看精选”筛选真正接入后端
- 补充首页与管理后台相关测试
- 为精选状态更新时间、排序优先级提供明确规则
- 为下载成功后累计安装的最小统计方案补充测试

### 4.3 本次明确不做

- 不恢复 Convex 时代的 badge/batch 复杂模型
- 不实现多种运营批次体系，仅支持 `highlighted` 单一精选状态
- 不实现精选历史审计页
- 不实现面向普通用户的精选申请流程
- 不新增推荐算法或人工打分系统
- 不实现完整的设备级安装上报体系
- 不实现“当前安装数”去重统计
- 不实现安装卸载、设备活跃或存量安装回填逻辑

## 5. 问题定义

### 5.1 首页空展示

当前首页的“精选技能”和“热门技能”不是接口无数据，而是页面代码直接使用空数组，导致用户看到：

- 还没有精选技能
- 还没有技能，来发布第一个吧

这与实际数据库已有 skill 数据不一致。

### 5.2 `highlighted` 概念断裂

当前 `highlighted` 在产品中是一个半残留状态：

- 前端文案和筛选保留了“精选”
- 首页有“精选技能”展示位
- 但 Go 后端没有对应字段与接口
- 管理后台没有运营入口

因此它目前不是一个真实产品能力，而只是前端残留概念。

### 5.3 安装统计语义失真

当前安装统计存在语义和实现不一致：

- CLI `install` 实际会请求下载接口并成功安装 skill
- 后端下载接口当前只会累计 `stats_downloads`
- 后端没有任何地方累计 `stats_installs`
- 前端详情页却展示“当前安装 / 累计安装”两项指标

因此，当前详情页中的安装数字并不可信，属于前端展示领先于后端能力的状态。

### 5.4 管理后台作者信息可读性不足

当前 `/management` 的 skill 列表作者栏仍可能展示内部 UID 或 owner handle 回退值，而不是后台运营最需要识别的飞书授权邮箱。

这会导致：

- 后台无法快速确认 skill 归属的组织账号
- 精选运营、删除恢复等后台操作缺少稳定的人类可读作者标识
- 飞书授权已经拿到邮箱信息，但管理页没有充分利用

### 5.5 公开用户页身份信息可读性不足

当前 `/u/:handle` 的用户信息区域仍使用 `@handle` 作为主要身份展示，而 handle 在飞书 OAuth 场景下可能就是 `ou_xxx` 这类 UID 风格值。

这会导致：

- 公开页面中的用户身份信息可读性不足
- 用户页与管理页对同一账号的展示规则不一致
- 系统已经持有邮箱信息，但公开资料页没有优先使用

## 6. 产品方案

### 6.1 数据模型

建议在 `skills` 表中新增布尔字段，例如：

- `is_highlighted BOOLEAN NOT NULL DEFAULT FALSE`

该字段表示 skill 是否处于精选状态。

本次不引入 badge 表或 batch 枚举，以最小实现满足首页与管理需求。

本次对安装统计同样采用最小方案，不引入 install event 表或设备级去重模型。

### 6.2 首页展示策略

首页“精选技能”：

- 查询 `highlighted = true` 的 skill
- 默认只展示活跃、未删除的 skill
- 数量可先控制为固定上限，例如 6 个
- 排序建议优先按 `updated_at DESC`

首页“热门技能”：

- 读取活跃、未删除 skill
- 按下载量降序展示
- 数量可先控制为固定上限，例如 6 个

### 6.3 管理后台策略

管理后台 skill 列表中应增加：

- 当前是否精选的状态展示
- “设为精选”按钮
- “取消精选”按钮
- 作者栏优先展示已获取的飞书授权邮箱

仅 superuser 或具备 management 权限的后台用户可以操作。

公开用户页用户信息区域应遵循同一套展示原则：

- 优先展示飞书授权邮箱
- 邮箱缺失时再回退到 `@handle`

### 6.4 列表页筛选策略

现有技能列表页的 `highlighted` 筛选参数应真正生效：

- 当前端传 `highlighted=1` 时
- 后端只返回 `is_highlighted = true` 的技能

这样首页、技能列表页和管理后台共享同一套精选语义。

### 6.5 安装统计最小方案

本次安装统计按“最小可落地”策略处理：

- CLI 安装仍沿用当前下载接口
- 后端在 ZIP 下载成功后，除累计 `stats_downloads` 外，同步累计 `stats_installs`
- 这里的 `stats_installs` 语义定义为“累计安装次数”
- 本次不尝试统计“当前安装数”

因此，前端详情页本次应做如下收口：

- 隐藏“当前安装”
- 仅展示“累计安装”
- 展示值直接使用后端累计的 `stats_installs`

这样可以保证展示出来的指标是后端确实能维护的真实数字，而不是虚假的双指标。

## 7. 接口要求

### 7.1 公共接口

现有 `GET /api/v1/skills` 应支持：

- `highlighted=1` 或等价布尔参数，用于筛选精选 skill

返回结果中的 skill 项建议包含：

- `highlighted: boolean`

至少在管理接口中必须返回该字段；公共列表接口是否一并返回，可根据前端使用便利性决定，但语义应保持一致。

对于 skill 统计字段，本次要求：

- `stats.downloads` 继续表示下载次数
- `stats.installs` 明确表示累计安装次数

前端不得再假定存在独立的 `installsCurrent` 后端来源，除非后续单独立项实现。

### 7.2 管理接口

建议新增统一接口：

- `POST /api/v1/admin/skills/{slug}/highlighted`

请求体：

```json
{ "highlighted": true }
```

或：

```json
{ "highlighted": false }
```

接口行为：

- `true` 表示设为精选
- `false` 表示取消精选

也可以拆成两个接口，但统一接口更简单。

管理列表与详情接口中的 owner 摘要本次还应明确返回：

- `email`

前端管理页展示规则：

- 优先展示飞书授权邮箱
- 若邮箱缺失，再回退到 handle 或其他现有字段

公开用户资料接口本次需要支持：

- `email`

前端 `/u/:handle` 页面展示规则：

- 优先展示邮箱
- 若邮箱缺失，再展示 `@handle`

## 9. 主要风险

### 9.1 首页与列表页语义不一致

如果首页“精选技能”和列表页 `highlighted` 筛选不是同一字段驱动，后续会继续出现数据不一致。

### 9.2 管理入口缺失导致运营失效

如果只恢复首页展示、不补管理开关，那么 `highlighted` 仍无法稳定运营，只能依赖临时 SQL 或手工改库。

### 9.3 字段扩散

如果公共接口、管理接口、前端类型没有统一 `highlighted` 命名，后续容易出现 `isHighlighted` / `highlighted` / `batch` 并存，增加维护成本。

### 9.4 安装指标命名继续混乱

如果本次后端只维护累计安装，但前端仍继续展示“当前安装 / 累计安装”双指标，会继续产生产品误导。

### 9.5 管理后台作者字段继续展示 UID

如果本次不同时收口 `/management` 的作者展示逻辑，后台虽然补齐了精选开关，但运营侧仍需要依赖 UID 识别作者，实际可用性仍然偏低。

### 9.6 公开用户页继续展示 UID 风格 handle

如果 `/u/:handle` 仍继续优先显示 `ou_xxx` 这类 handle，用户页的人类可读性依然不足，并且会和管理页的邮箱优先展示规则再次分叉。

因此本次必须明确：

- 后端只对外提供可落地的累计安装语义
- 前端不再展示当前安装

## 10. 验收标准

本次需求完成后，应满足以下验收结果：

1. 首页“精选技能”不再使用占位空数组，而是显示真实精选 skill。
2. 首页“热门技能”不再使用占位空数组，而是显示真实热门 skill。
3. 数据库中的 skill 可以持久化存储精选状态。
4. 管理后台可以对单个 skill 执行“设为精选”和“取消精选”。
5. 管理后台列表可以清楚看到 skill 当前是否为精选。
6. `GET /api/v1/skills` 在携带 `highlighted` 过滤参数时，能够只返回精选 skill。
7. 技能列表页现有“仅看精选”筛选可以真正生效。
8. 首页“精选技能”、技能列表页精选筛选、管理后台精选配置三者基于同一套后端字段和语义工作。
9. CLI 安装触发的下载成功后，会同步使 skill 的 `stats.installs` 增长。
10. 详情页不再展示“当前安装”这个不可信指标。
11. 详情页展示的“累计安装”与后端 `stats.installs` 一致。
