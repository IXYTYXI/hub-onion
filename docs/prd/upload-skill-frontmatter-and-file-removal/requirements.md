# 上传页自动解析 SKILL.md 与文件删除交互需求文档

## 1. 文档目的

本文档用于定义 ClawHub 上传页 `/upload` 中三项增强能力的需求边界，作为后续产品确认、技术设计、开发拆解和验收的依据：

- 在用户选择上传文件夹或压缩包后，自动解析其中 `SKILL.md` 的 frontmatter `name`
- 在上传文件列表中支持删除单个文件，并在删除后即时重算校验结果
- 在发布前后识别 `slug` 是否已存在，并在“新建 skill / 发布新版本 / slug 被占用 / 版本已存在”之间给出明确引导

本文档基于当前 Go 后端 + 前端上传页现状编写，不涉及恢复或复用旧 Convex 依赖。

## 2. 背景

当前上传页已经具备以下能力：

- 支持选择文件夹、拖拽文件夹、拖拽文件或上传压缩包
- 能自动展开 zip / tar.gz / gz，并自动剥离最外层包装目录
- 能展示上传后的文件列表
- 能校验是否包含 `SKILL.md`、是否为文本文件、总大小是否超过 50MB
- 能在校验通过后一次性将 `payload + files` 提交给新后端发布接口

但当前仍有三个明显的产品缺口：

- 用户上传后，`displayName` 和 `slug` 仍需要手工填写，系统没有利用 `SKILL.md` 中已存在的 `name`
- 一旦文件列表中混入不合法文件，用户只能回到本地目录删除后重新上传，无法在页面内快速修正
- 当 `slug` 已存在、版本已重复或当前用户其实应该发布“新版本”时，页面仍可能只给出通用失败提示，无法告诉用户下一步该怎么做

这三个问题都会直接增加上传操作成本，尤其影响目录上传、压缩包上传以及已有 skill 的持续迭代场景。

## 3. 核心目标

本次需求的核心目标如下：

1. 在上传页本地读取 `SKILL.md` frontmatter 中的 `name`
2. 基于解析出的 `name` 自动补全上传表单中的默认值
3. 保持用户手动输入的优先级，避免自动解析覆盖用户已确认的内容
4. 在文件列表中增加逐行删除能力
5. 删除文件后立即刷新上传页的全部本地校验状态
6. 在输入 `slug` 和提交发布时，明确区分“可新建 / 当前用户发布新版本 / slug 被他人占用 / 版本已存在”
7. 将可恢复的业务冲突翻译成字段级或表单级引导，而不是只显示通用服务端错误
8. 保持现有发布接口协议不变，不因这些交互能力修改后端入参

## 4. 范围

### 4.1 本次必须覆盖

- 上传页在文件展开完成后尝试定位 `SKILL.md` 或 `skills.md`
- 读取并解析 frontmatter 中的 `name`
- 基于 `name` 自动生成 `slug`
- 在合适条件下自动填充 `displayName`
- 文件列表中每一行提供删除操作
- 在用户输入 `slug` 后，系统尝试识别该 `slug` 是否已存在
- 当 `slug` 属于当前用户时，页面切换为“发布新版本”语义
- 当 `slug` 属于其他用户时，页面明确提示已被占用并阻止发布
- 当版本号已存在时，页面明确提示需要升级版本号，而不是显示通用服务端错误
- 删除后立即重算：
  - 文件数量
  - 文件总大小
  - 是否包含必需的 `SKILL.md`
  - 非文本文件校验
  - 发布按钮可用状态
  - 页面中的校验文案

### 4.2 本次建议覆盖

- 在自动填充发生时，提供轻量提示，帮助用户理解字段来源
- 删除 `SKILL.md` 时给予明确的校验反馈
- 在版本输入区域提示当前已存在的最新版本
- 在提交失败时，将已知业务冲突翻译为可执行的提示文案
- 对压缩包展开后的文件与目录上传后的文件保持同一套行为
- 为自动解析和删除行为补充单元测试或路由测试

### 4.3 本次明确不做

- 不修改 `/api/v1/skills` 发布接口协议
- 不要求后端在发布时二次解析 `SKILL.md` 来回填 `displayName`
- 不新增服务端 frontmatter 存储要求
- 不引入多候选 skill 包选择器
- 不实现“撤销删除”或“批量删除”能力
- 不新增新的上传模式或新的必填表单字段
- 不从 `convex/` 目录继续复用旧前端或旧后端依赖
- 不在本次需求中引入新的发布协议或强制新增专用“上传预检查”接口

## 5. 问题定义

### 5.1 已有 metadata 没被利用

上传内容中的 `SKILL.md` 往往已经包含：

- `name`
- `description`
- 其他 frontmatter 信息

但上传页目前没有读取这些内容，导致用户在页面中重复填写已经存在的信息。

### 5.2 本地修正成本过高

当前文件列表只是展示，不支持编辑。若出现以下情况：

- 不小心带上了截图、二进制文件
- 带上了调试产物
- 上传后才发现某个文件不应该包含在当前版本中

用户只能回到本地目录处理，再重新选择目录或压缩包，效率较低。

### 5.3 迁移后的共享边界需要保持干净

项目已从 Convex 迁移到 Go 后端，当前这类 frontmatter 解析能力虽然在旧代码中存在，但本次需求不应重新把前端逻辑耦合回 `convex/` 目录。

因此，本次需求要求：

- 纯解析逻辑放到真正的共享或前端本地公共位置
- 不影响当前前后端交互边界

### 5.4 可恢复冲突没有被翻译成用户动作

当前发布失败场景中，至少存在以下几类本质不同的业务情况：

- `slug` 不存在，可以新建 skill
- `slug` 已存在，且属于当前用户，本次应视为发布新版本
- `slug` 已存在，但属于其他用户，应要求更换标识
- 当前 `version` 已存在，应要求升级版本号

这些情况在用户动作上完全不同，但如果页面只展示通用错误，用户无法判断应该：

- 改 slug
- 改版本号
- 继续作为新版本发布
- 还是稍后重试

因此，本次需求要求把业务冲突翻译成明确交互，而不是把所有冲突都归为“API request failed”。

## 6. 产品方案

### 6.1 自动解析触发时机

自动解析应发生在上传页“文件展开完成之后、本地校验之前或与校验同轮进行时”。

适用场景包括：

- 选择文件夹
- 拖拽文件夹
- 上传 zip / tar.gz / gz 并完成展开
- 重新选择一批文件替换当前列表

如果本轮文件列表中不存在 `SKILL.md` / `skills.md`，则不触发自动解析。

### 6.2 目标文件识别规则

本次需求沿用当前上传页对必需文件的识别规则：

- `SKILL.md`
- `skills.md`

大小写匹配按当前页面已有逻辑保持兼容。

若存在多个候选文件，本次按当前上传页的单列表模型处理：

- 优先选择规范化路径后最靠前的有效 `SKILL.md` 候选
- 不新增“选择哪个 skill 包”的额外交互

### 6.3 frontmatter 解析规则

系统应仅读取 markdown 顶部标准 frontmatter 区块中的 `name` 字段。

要求如下：

- 仅使用 `name` 作为本次自动补全来源
- `name` 为空、不是字符串、或解析失败时，视为无可用值
- 解析失败不能阻断上传，也不能报全局错误
- 解析失败时页面保持现有手工填写流程

本次不要求基于 `description`、`metadata` 等其他字段做额外自动填充。

### 6.4 自动填充规则

系统解析出有效 `name` 后，按以下规则处理：

#### 6.4.1 slug

- 若当前 `slug` 为空，则根据 `name` 自动生成 slug
- 生成规则沿用现有 slug 规范：
  - 转小写
  - 非字母数字字符替换为短横线
  - 去除首尾短横线
- 若用户已经手动输入过 `slug`，则后续自动解析不得覆盖

#### 6.4.2 displayName

- 若当前 `displayName` 为空，则自动填入一个基于 `name` 的默认展示值
- 若用户已经手动输入过 `displayName`，则后续自动解析不得覆盖

### 6.5 用户手动输入优先级

用户手工编辑必须高于自动解析结果。

具体规则：

- 自动填充只应作用于“当前仍为空且未被用户手工修改过”的字段
- 一旦用户手工改过 `slug` 或 `displayName`，后续重新选文件或重新解析时不得自动覆盖
- 若用户主动清空字段，是否重新允许自动填充，建议作为实现细节处理，但不得造成明显困惑

### 6.6 文件列表删除交互

文件列表中每一行都应提供一个明确的删除入口。

建议交互：

- 文件名在左侧
- 删除按钮在右侧
- 删除按钮文案可直接使用“删除”

删除操作应立即生效，无需额外弹窗确认。

本次不要求提供：

- 二次确认弹窗
- 批量删除
- 删除后撤销

### 6.7 删除后的联动行为

删除任意文件后，页面应立即基于剩余文件列表重算并刷新：

- 文件数统计
- 总大小显示
- 校验结果列表
- 相关提示文案
- 发布按钮禁用状态

关键场景要求：

- 删除非文本文件后，对应“请移除非文本文件”错误应立即消失
- 删除 `SKILL.md` 后，应立即出现“`SKILL.md` 不能为空”或等价校验提示
- 删除最后一个文件后，应立即回到“尚未选择文件”状态

### 6.8 自动解析与删除的关系

自动解析与删除需要遵循一致的数据源，即当前页面中的实际 `files` 列表。

要求如下：

- 初次上传完成后，自动解析基于当下文件列表执行
- 删除文件后，如果删除的是 `SKILL.md`，则当前这轮自动解析结果不应继续被视为有效来源
- 但已被用户手工确认过的字段值，不因删除文件而强制清空

产品上建议：

- 删除 `SKILL.md` 后保留当前表单字段值
- 通过校验区明确提示“当前文件列表缺少必需文件，不能发布”

这样可以避免用户输入被系统突然清空，同时保持发布前约束清晰。

### 6.9 slug 存在性与版本冲突引导

系统在用户输入 `slug` 后，应尝试判断当前发布意图属于以下哪一类：

- 新建 skill
- 当前用户为已有 skill 发布新版本
- `slug` 已被其他用户占用

建议采用如下交互：

- 当 `slug` 不存在时：
  - 提示：`该标识可用于新建 skill`
- 当 `slug` 已存在且属于当前用户时：
  - 提示：`你已发布过该 skill，本次将作为新版本发布`
  - 版本区域提示当前最新版本
  - 发布按钮文案可切换为 `发布新版本`
- 当 `slug` 已存在但属于其他用户时：
  - 提示：`该标识已被占用，请更换 slug`
  - 发布按钮应禁用

### 6.10 提交失败后的冲突翻译

即使页面已在提交前做出引导，最终仍应以后端返回为准。

系统对以下失败场景应提供明确提示：

- `slug` 属于其他用户
  - 提示用户更换 `slug`
- 当前用户重复发布同一 `version`
  - 提示用户升级版本号
- 当前用户正在向已有 skill 发布新版本但校验未通过
  - 提示用户继续在“发布新版本”语义下修正输入
- 仅在真实服务端异常时显示通用失败提示

## 7. 交互规则清单

### 7.1 首次上传成功展开文件

- 页面展示文件列表
- 若存在 `SKILL.md`，尝试解析 `name`
- 若解析成功且 `slug` 为空，自动填入 slug
- 若解析成功且 `displayName` 为空，自动填入 displayName
- 校验区域同步显示最新结果

### 7.2 用户已手工输入，再重新上传

- 新文件列表替换旧文件列表
- 可重新尝试解析 `SKILL.md`
- 但不得覆盖用户已手工修改过的 `slug` / `displayName`

### 7.3 用户删除非文本文件

- 文件立即从列表中消失
- 非文本文件报错立即消失
- 其他校验项同步保留或更新

### 7.4 用户删除 `SKILL.md`

- 文件立即从列表中消失
- 页面继续保留当前 `slug` / `displayName`
- 校验区立即提示缺少必需文件
- 发布按钮立即禁用

### 7.5 用户删除最后一个文件

- 文件列表回到空状态
- 文件数与总大小归零
- 校验区恢复“请至少添加一个文件”等空状态校验
- 发布按钮禁用

### 7.6 用户输入一个未被占用的 slug

- 系统尝试检查该 `slug`
- 页面提示该标识可用于新建 skill
- 发布按钮保持可用，前提是其他校验已通过

### 7.7 用户输入一个属于自己的已有 slug

- 系统尝试检查该 `slug`
- 页面切换为“发布新版本”语义
- 版本区域展示当前最新版本
- 若其他校验通过，允许继续发布

### 7.8 用户输入一个被他人占用的 slug

- 系统尝试检查该 `slug`
- 页面明确提示该标识已被占用
- 发布按钮禁用

### 7.9 用户提交了一个已存在的版本号

- 若当前 `slug` 属于该用户且 `version` 已存在
- 页面应提示“该版本已存在，请填写更高版本”
- 焦点应回到版本号输入区域或给予明显字段级反馈

## 8. 验收标准

### 8.1 自动解析

- 上传包含 `SKILL.md` 的目录或压缩包后，系统可尝试读取 frontmatter `name`
- 当 `slug` 为空时，系统会基于 `name` 自动生成合法 slug
- 当 `displayName` 为空时，系统会自动填充默认显示名称
- 若用户已手工修改字段，重新上传或重新解析不会覆盖这些值
- `SKILL.md` 无 frontmatter、frontmatter 无 `name`、或解析失败时，页面仍可正常继续手工填写

### 8.2 删除交互

- 文件列表每一项均可单独删除
- 删除后文件立即从列表消失
- 删除后页面所有校验状态立即更新
- 删除非文本文件后，相关报错立即消失
- 删除 `SKILL.md` 后，发布按钮立即不可用

### 8.3 发布冲突引导

- 当用户输入一个未占用的 `slug` 时，页面能提示其可新建
- 当用户输入一个属于自己的已有 `slug` 时，页面能提示本次将作为新版本发布
- 当用户输入一个被他人占用的 `slug` 时，页面能明确提示更换 `slug`
- 当用户提交重复版本号时，页面能明确提示升级版本号，而不是只显示通用服务端错误
- 仅在真实服务端异常时展示通用失败提示

### 8.4 非目标确认

- 发布接口请求格式保持不变
- 后端无需新增字段解析逻辑即可兼容本次需求
- 前端不再从 `convex/` 目录引用纯解析工具

## 9. 风险与约束

- `name` 的内容可能并不天然适合作为最终展示名或 slug，因此自动填充只能是默认值，不能替代用户最终确认
- 若一个上传包中存在多个 `SKILL.md` 候选，本次不增加复杂选择器，只能使用约定优先级处理
- 删除交互是本地状态编辑能力，必须保证与拖拽、目录上传、压缩包展开后的数据结构一致
- 前端若直接复用旧 `convex/` 目录代码，会重新污染迁移边界，因此本次要求将解析逻辑落到新的共享位置
- 若后端继续把所有业务冲突都返回为 500，前端只能做有限兜底，因此最终仍需要服务端提供更稳定的冲突语义

## 10. 实施清单

### 10.1 文档与方案

- 明确上传页自动填充的字段范围仅为 `slug` 和 `displayName`
- 明确“用户手工输入优先于自动解析”的覆盖规则
- 明确删除 `SKILL.md` 后保留表单值但禁止发布的产品策略
- 明确 `slug` 检查后的三种页面语义：可新建、发布新版本、被占用
- 明确重复版本号应映射为版本升级引导，而不是通用错误

### 10.2 前端能力拆分

- 在 `src/lib/` 或新的共享位置新增纯 frontmatter 解析工具
- 上传页文件展开完成后接入 `SKILL.md` 自动解析流程
- 为 `slug` / `displayName` 增加“是否已被用户手工修改”的本地状态控制
- 在文件列表渲染中加入逐行删除按钮
- 将删除行为接入现有 `files` 状态管理与校验逻辑
- 为上传页补充 `slug` 存在性检查与页面语义切换
- 为当前用户已有 skill 场景补充版本信息查询与提示
- 为提交失败补充业务错误映射层

### 10.3 文案与提示

- 补充必要的自动填充提示文案
- 补充文件删除按钮文案
- 补充 `slug` 可用、新版本发布、slug 被占用、版本已存在等提示文案
- 确认删除后校验提示是否沿用现有上传页文案体系

### 10.4 测试建议

- 补充“上传后自动解析 `name`”测试
- 补充“用户手工输入后不被自动覆盖”测试
- 补充“删除非文本文件后校验恢复”测试
- 补充“删除 `SKILL.md` 后禁止发布”测试
- 补充“删除最后一个文件后回到空状态”测试
- 补充“slug 可新建 / 归属自己 / 被占用”的交互测试
- 补充“重复版本号映射为升级提示”的交互测试

## 11. 结论

本需求本质上是对上传页现有本地文件状态能力的补强，不需要改动后端协议，核心价值在于两点：

1. 利用 `SKILL.md` 已有 metadata，减少重复填写
