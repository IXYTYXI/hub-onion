# 飞书授权接入需求文档

## 1. 文档目的

本文档用于定义 ClawHub 当前项目中接入飞书授权的最终需求，作为后续技术设计、任务拆解和联调验收的依据。

本文档基于当前仓库代码现状编写，不是抽象讨论：

- 当前后端已经具备邮箱登录、外部 OAuth Provider、JWT Session、CLI API Token 能力
- 当前前端已经基于 `/api/v1/users/me` 感知登录状态
- 当前管理端已经依赖本地用户、角色和 `isSuperuser` 判断权限
- 当前产品已确认采用“飞书主登录、邮箱辅助保留”的最终方案

## 2. 背景与核心问题

当前系统面临的实际业务问题：

- 目标用户主要会在飞书客户端内访问产品，因此需要低摩擦免登
- 平台又不能把所有授权能力直接交给飞书身份，因为管理权限仍需本地控制
- 当前系统存在邮箱身份、外部身份并存的现实，需要避免它们被误理解成两套独立账号体系

这里需要明确一个新边界：

- 飞书客户端内免登与普通浏览器中的飞书授权登录，是两条不同的登录链路
- 飞书工作台点击应用后唤起浏览器进入平台，属于额外增强场景，不等同于普通浏览器登录按钮

本次需求要解决的核心问题：

1. 如何让飞书成为平台主登录方式
2. 如何让邮箱作为辅助能力和兼容入口继续存在
3. 如何保证未绑定邮箱的飞书账号不能拥有管理权限
4. 如何让已有邮箱管理员平滑切到飞书登录而不丢失权限

## 3. 当前系统现状

### 3.1 认证现状

当前 Go 后端具备以下认证能力：

- 邮箱注册、激活、登录
- GitHub OAuth 登录
- GitLab OIDC/OAuth 登录
- 平台本地 JWT Session Cookie：`clawhub_session`
- CLI API Token

这说明当前系统已经具备“本地用户体系 + 多登录来源”的基础结构。

这里必须明确：

- 飞书身份和邮箱身份都不是独立账号主体
- 平台真正的账号主体始终是 ClawHub 本地用户 `users.id`
- 飞书登录、邮箱登录都只是进入同一个本地用户的不同身份入口

### 3.2 用户与权限现状

当前用户系统的特点：

- 平台始终维护自己的本地用户 `users`
- 外部身份可以映射到本地用户
- 管理端权限基于本地 `role` 和 `isSuperuser`
- 管理权限目前不是由某个外部 IdP 直接决定

结论：

- 飞书可以接管主登录
- 但管理员与超级管理员权限仍必须由 ClawHub 本地控制

### 3.3 前端现状

当前前端登录页仍以邮箱注册/登录为主，前端登录态依赖：

- `/api/v1/users/me`
- 浏览器 Cookie

这意味着，只要飞书登录最终也能拿到本地 Session Cookie，前端业务协议无需整体重写。

## 4. 最终产品目标

本次确认的目标如下：

1. 飞书授权作为平台主登录方式
2. 飞书客户端内优先走 `requestAccess` 免登
3. 普通浏览器支持飞书 OAuth 登录，且该跳转链路与前端 API 代理分离
4. 已有邮箱用户支持绑定飞书身份
5. 不使用邮箱字段做自动合并主键
6. 飞书登录成功后，仍由 ClawHub 后端签发本地 Session
7. 未绑定邮箱的飞书账号默认只能拥有普通用户权限
8. 管理员和超级管理员必须依附“已绑定邮箱”的本地账号

## 5. 范围

### 5.1 本次必须覆盖

- 飞书客户端内 H5 免登接入方案
- 普通浏览器飞书 OAuth 登录方案
- 飞书主登录与浏览器 OAuth 分流方案
- 邮箱账号绑定飞书方案
- 飞书主登录用户补充/绑定邮箱的方案
- 本地用户与飞书身份绑定规则
- 管理员与超级管理员权限规则
- 对前端登录页、用户页、设置页、后端认证层的影响分析

### 5.2 本次建议覆盖

- 飞书身份字段模型设计
- 邮箱绑定状态模型设计
- 账号冲突、绑定失败、权限拒绝的兜底规则
- 管理端对登录来源和绑定状态的展示规则

### 5.3 本次明确不要求

- 直接编码实现
- 基于飞书组织架构自动同步平台角色
- 使用飞书邮箱字段直接作为平台账号主键
- 使用飞书 Access Token 直接作为平台会话
- CLI 改为直接走飞书 OAuth

## 6. 核心产品方案

### 6.1 登录主策略

最终策略如下：

- 飞书授权作为主登录方式
- 飞书客户端内：优先走 `requestAccess` 免登
- 普通浏览器：支持标准飞书 OAuth 重定向登录
- 邮箱：继续作为辅助能力与兼容入口存在
- 新用户：可直接使用飞书首次登录创建本地账号
- 已有邮箱用户：可在平台内绑定飞书身份

必须明确：

- 飞书登录和邮箱登录不是两套账号
- 两者最终都必须收敛到同一个本地用户主体
- 平台业务数据、权限、资料都只挂在本地用户上
- 飞书客户端内免登与普通浏览器飞书 OAuth 登录共享同一套本地用户映射和本地 Session 机制，但前端触发方式不同
- 飞书工作台唤起浏览器进入平台不作为本期必须能力，后续如需支持，应单独设计入口与回调

### 6.2 身份识别策略

飞书身份识别规则：

- 不使用邮箱做自动账号合并
- 外部身份主键优先使用 `union_id`
- 若某些场景无法拿到 `union_id`，允许回退到 `open_id`
- 同时保存 `tenant_key` 作为租户识别字段

原因：

- 邮箱和手机号不是强身份字段，不适合作为自动合并主键
- `union_id` 更适合作为飞书主登录下的稳定身份键
- `open_id` 适合单应用内唯一识别
- `tenant_key` 有助于识别用户所属飞书租户

### 6.3 会话策略

飞书登录成功后：

- 后端仍创建或复用本地用户
- 后端仍签发本地 JWT Session
- 浏览器仍以 `clawhub_session` Cookie 保存登录态
- 业务 API 和前端鉴权协议不做破坏性变更

### 6.4 账号绑定策略

本次必须支持两类绑定：

- 已有本地用户绑定飞书身份
- 飞书主登录的本地用户绑定邮箱身份

绑定规则：

- 仅已登录用户可以主动执行绑定
- 绑定操作必须验证目标身份尚未被其他本地用户占用
- 若飞书身份已被占用，必须报错并阻止绑定
- 平台不根据邮箱自动把两个账号合并
- 邮箱绑定必须验证邮箱所有权

绑定后的语义：

- 绑定不会创建第二个账号主体
- 绑定只是给同一个本地用户增加一种可登录身份
- 用户的技能、设置、权限始终跟随本地用户，不跟随登录方式

### 6.5 邮箱链路职责重定义

在飞书主登录模型下，邮箱相关链路必须重新定义职责。

#### 6.5.1 邮箱注册

邮箱注册不应再被视为平台主账号创建入口。  
在最终方案里，邮箱注册的主要职责应改为：

- 给当前已登录本地用户发起邮箱绑定
- 启动邮箱验证流程

在业务语义上，更接近：

- “绑定邮箱”

而不是：

- “创建一套独立邮箱账号”

#### 6.5.2 邮箱激活

邮箱激活链路应保留，但职责改为：

- 验证邮箱所有权
- 完成邮箱绑定
- 把当前本地用户更新为“已绑定邮箱”状态

该链路是管理权限前置条件的重要组成部分。

#### 6.5.3 邮箱登录

邮箱登录链路应保留，但明确降级为：

- 邮箱辅助登录入口

其职责是：

- 作为辅助方式进入已有本地用户
- 为历史邮箱用户提供兼容入口
- 为管理员提供辅助兜底入口

邮箱登录不应用于再创建第二套账号主体。

### 6.6 管理权限策略

这是本方案的硬约束。

必须明确以下原则：

- 飞书只负责认证“你是谁”
- ClawHub 本地系统负责授权“你能做什么”
- 管理权限必须绑定本地用户
- 只有绑定了邮箱的本地用户，才允许拥有管理权限
- 纯飞书账号即使可以登录，也不能直接成为管理员或超级管理员

本次要求：

- 当前 `role` / `isSuperuser` 机制继续保留
- 管理权限授予前必须校验邮箱已绑定
- 平台必须支持把飞书身份绑定到已有邮箱管理员本地用户
- 未绑定邮箱时，即使飞书身份满足其他条件，也不得直接授予管理权限

### 6.7 用户资料展示策略

飞书登录后，平台可从飞书用户信息中获取并用于展示的字段包括：

- `name`
- `avatar_url`
- 可选 `email`

用于身份识别但不建议公开展示的字段：

- `open_id`
- `union_id`
- `tenant_key`

敏感或不建议作为登录凭证的字段：

- `email`
- `mobile`

补充展示约束：

- 飞书原始标识仅允许后端存储和内部匹配，不应在前端用户页面直接展示
- 设置页不得直接展示 `open_id`、`union_id`、`tenant_key`、飞书 `user_id` 等关键标识
- 像 `ou_4a3321fb363a87913a7fc408e4945e05`、`tenant_key: 2d25cdd5610f575e` 这类值不得直接暴露给用户
- 用户页、用户触发消息、欢迎文案应优先使用用户姓名、显示名和已绑定邮箱
- `employee_no` 如无明确业务需求，本期不作为前台展示字段

## 7. 主要使用场景

### 场景一：飞书内新用户首次进入

1. 用户在飞书客户端内打开 ClawHub
2. 前端检测运行环境并发起飞书免登
3. 后端根据飞书身份创建本地用户，并默认直接激活为 `active`
4. 后端签发平台 Session
5. 用户进入已登录状态

验收重点：

- 全程不要求用户额外输入邮箱或密码
- 平台账号成功创建
- 后续页面访问保持登录状态
- 该账号默认不具备管理权限

### 场景二：已有邮箱用户首次在飞书内登录

1. 用户此前通过邮箱在平台中已存在账号
2. 用户在飞书客户端内首次访问平台
3. 系统不自动按邮箱合并
4. 用户需要在已登录邮箱账号状态下主动绑定飞书
5. 绑定后，后续飞书登录进入同一本地用户

验收重点：

- 不发生无提示自动合并
- 不丢失原有技能、设置、权限
- 绑定后两种登录方式都进入同一个本地用户

### 场景三：飞书主登录用户补充邮箱

1. 用户先通过飞书主登录进入平台
2. 该本地用户当前没有绑定邮箱身份
3. 用户在设置页补充并验证邮箱
4. 邮箱绑定成功后，账号可满足后续管理权限前置条件

验收重点：

- 邮箱绑定需完成验证
- 绑定前后用户主体不变化
- 绑定邮箱后才允许进入管理权限候选范围
- 飞书登录和邮箱登录都进入同一个本地用户

### 场景四：普通浏览器用户访问

1. 用户不在飞书客户端内访问
2. 登录页默认提供飞书登录入口，并保留邮箱兼容入口
3. 普通浏览器下飞书登录通过独立 OAuth 跳转地址发起，不经过 API 代理

验收重点：

- 普通浏览器可直接发起飞书登录
- 非飞书环境不误触发 H5 免登逻辑
- 浏览器 OAuth 导航链路与 API 代理链路分离

### 场景五：邮箱辅助登录进入已有本地用户

1. 用户不在飞书客户端内访问平台
2. 用户使用邮箱辅助登录
3. 后端按邮箱找到已存在的本地用户
4. 用户进入该本地用户，而不是创建新的账号主体

验收重点：

- 邮箱登录进入已有本地用户
- 不生成新的平行账号
- 对历史邮箱用户保持兼容

### 场景六：管理员使用飞书登录

1. 管理员已有本地账号与管理权限
2. 该管理员本地用户已绑定邮箱身份
3. 管理员绑定飞书身份
4. 平台把该飞书身份映射到原本地用户
5. 后续飞书登录后，管理员仍具备原管理权限

验收重点：

- 管理权限不因登录方式切换而丢失
- `isSuperuser` / `role` 行为与原来一致
- 未绑定邮箱的飞书账号不能进入管理能力范围

## 8. 状态机规则

为了避免“飞书账号”和“邮箱账号”被误解为两套主体，平台后续应统一按本地用户状态理解认证与权限。

### 8.1 状态 A：未登录

特征：

- 没有本地 Session
- 没有关联到任何本地用户

允许动作：

- 飞书主登录
- 邮箱辅助登录

禁止动作：

- 绑定飞书
- 绑定邮箱
- 访问管理能力

### 8.2 状态 B：已通过飞书登录，未绑定邮箱

特征：

- 已有关联的本地用户
- 已绑定飞书身份
- 未绑定邮箱

允许动作：

- 正常使用普通用户功能
- 发起绑定邮箱
- 登出

禁止动作：

- 获得管理权限
- 访问管理后台

### 8.3 状态 C：已绑定邮箱的普通用户

特征：

- 已有关联的本地用户
- 已绑定邮箱
- 已绑定飞书或可选绑定飞书
- 角色仍为普通用户

允许动作：

- 飞书登录进入
- 邮箱辅助登录进入
- 正常使用普通用户功能

禁止动作：

- 访问管理后台

### 8.4 状态 D：已绑定邮箱的管理用户

特征：

- 已有关联的本地用户
- 已绑定邮箱
- 具备 `admin` / `moderator` / `isSuperuser`

允许动作：

- 飞书登录进入
- 邮箱辅助登录进入
- 访问管理能力

### 8.5 状态 E：仅邮箱进入的历史用户，尚未绑定飞书

特征：

- 已有关联的本地用户
- 已绑定邮箱
- 尚未绑定飞书

允许动作：

- 邮箱辅助登录进入
- 发起绑定飞书
- 若本地权限允许，可继续管理

## 9. 功能需求

### 9.1 前端需求

必须支持：

- 识别当前是否运行在飞书客户端内
- 在飞书客户端内优先尝试发起飞书免登
- 登录页提供飞书主登录入口，并保留邮箱兼容入口
- 用户设置页提供“绑定飞书”入口
- 用户设置页当前仅展示飞书绑定状态与飞书同步邮箱
- 对绑定成功、失败、已绑定、冲突、权限受限等状态给出明确提示
- 对未绑定邮箱的飞书用户，明确提示其不具备管理权限
- 设置页账号绑定区仅展示“已绑定飞书账号”和飞书同步邮箱等业务字段，不展示飞书原始标识
- 用户消息和用户页展示不得使用飞书关键 ID 作为用户可见文案
- 设置页个人资料区展示用户名和本地系统 UID，不展示飞书原始 UID

建议支持：

- 登录页在普通浏览器下可直接发起飞书 OAuth 登录
- 用户资料页展示用户名、本地 UID 和基础资料

### 9.2 后端需求

必须支持：

- 接收前端上传的飞书临时登录凭证 `code`
- 通过飞书 OpenAPI 换取 `user_access_token`
- 通过飞书用户信息接口获取用户身份
- 依据飞书身份查询或创建本地用户
- 创建本地 Session Cookie
- 普通浏览器登录与绑定链路支持通过独立 OAuth 导航地址发起
- 绑定飞书身份到当前已登录本地账号
- 绑定邮箱到当前已登录本地账号
- 在管理权限授予时校验邮箱绑定状态
- 飞书首次登录创建用户时直接设为 `active`

这里的实现要求必须统一为：

- 所有登录方式最终都落到同一个本地用户模型
- 不允许因为新增飞书登录而额外引入第二套用户主体

### 9.3 用户数据需求

系统必须至少保存以下飞书相关信息：

- provider：`feishu`
- provider subject：`union_id` 或 `open_id`
- `open_id`
- `union_id`
- `tenant_key`
- 飞书头像
- 飞书显示名
- 最近一次登录时间

系统必须具备以下邮箱相关状态：

- 是否已绑定邮箱
- 邮箱是否已验证

### 9.4 权限需求

系统必须满足：

- 用户角色仍然保存在本地数据库
- 管理端仍按本地用户判断权限
- 管理权限授予前必须校验是否已绑定邮箱
- 超级管理员识别不能绕过邮箱绑定前置条件
- 飞书身份变更不应隐式提升权限

### 9.5 邮箱链路需求

系统必须满足以下邮箱链路要求：

- 邮箱注册语义默认视为“发起邮箱绑定”
- 邮箱激活语义默认视为“验证邮箱并完成绑定”
- 邮箱登录语义默认视为“邮箱辅助登录进入已有本地用户”
- 邮箱链路不得默认生成与飞书用户平行的第二套账号主体

## 10. 非功能需求

### 10.1 兼容性

- 不破坏现有 `/api/v1/users/me` 协议
- 不破坏现有业务 API 的 Cookie 鉴权方式
- 不破坏现有 CLI Token 机制
- 不要求本次同步重写所有登录页和设置页结构

### 10.2 安全性

- 不在前端保存飞书长期 Token
- 不将飞书邮箱作为自动合并依据
- 绑定操作必须防止跨账号占用
- 邮箱绑定必须验证邮箱所有权
- 必须保留本地审计能力，记录绑定和登录事件

### 10.3 可维护性

- 不把飞书登录做成独立于现有认证体系的旁路系统
- 必须复用现有本地用户与本地 Session
- 管理权限规则必须在本地系统内可审计、可校验

## 11. 风险与约束

### 11.1 主要风险

- 飞书身份与现有邮箱账号的重复账号问题
- 管理员账号切换登录方式时的权限映射问题
- 飞书接口或字段权限不足导致资料字段不完整
- 飞书环境识别失败导致错误触发免登
- 邮箱绑定状态与管理权限判定不同步

### 11.2 约束

- 当前项目已有邮箱登录和审核流，不能一刀切废弃
- 当前管理端依赖本地用户权限，不适合直接改为飞书角色驱动
- 当前用户模型对外部身份支持有限，需要技术方案补齐
- 管理权限必须依附邮箱绑定这一业务规则，不能让纯飞书身份直接获得管理能力

## 12. 验收标准

满足以下条件视为本次需求定义完整：

1. 已定义飞书主登录和邮箱辅助登录的职责划分
2. 已定义账号绑定规则且明确不按邮箱自动合并
3. 已明确管理员和超级管理员必须绑定邮箱
4. 已明确纯飞书账号默认不具备管理权限
5. 已明确使用 `open_id` / `union_id` 进行身份识别，而非邮箱
6. 已明确会话层继续复用本地 JWT Session Cookie
7. 已明确邮箱注册 / 激活 / 登录在统一账号模型下的新职责
8. 已输出对应的技术设计方案
