# 去邮箱可见性改造技术方案文档

## 1. 设计目标

本文档给出 ClawHub 当前阶段“去掉基于邮箱的用户流程可见性”的技术方案，目标如下：

1. 不破坏现有后端协议与数据结构
2. 优先从前端收起邮箱与审核的产品可见性
3. 让飞书成为用户唯一可见的登录入口
4. 让管理后台不再承担用户审核前端入口职责
5. 用最小后端行为调整，避免普通用户感知审核流

## 2. 方案原则

本次方案坚持以下原则：

- 先收口可见性，再考虑后续删除能力
- 先减少用户感知，再处理内部结构
- 前端整块移除用户审核入口，不做半隐藏
- 后端接口先保留，避免本轮范围扩散
- 不考虑存量用户兼容问题

## 3. 当前实现分析

### 3.1 当前仍然暴露邮箱流程的位置

当前前端存在以下显性邮箱流程入口：

- 登录页中的邮箱辅助登录入口与邮箱密码表单
- 认证文案中对邮箱登录、邮箱未绑定、邮箱激活的描述
- 设置页中对邮箱与管理权限关系的公开说明

相关文件：

- `src/routes/auth/login.tsx`
- `src/copy/auth.ts`
- `src/routes/settings.tsx`
- `src/copy/settings.ts`

### 3.2 当前仍然暴露用户审核流程的位置

当前前端显性暴露了用户审核能力：

- 管理后台存在 `users` tab
- 页面会请求用户审核列表和详情接口
- 页面展示用户状态筛选
- 页面提供 approve / reject / disable / enable 操作

相关文件：

- `src/routes/management.tsx`
- `src/copy/management.ts`

### 3.3 当前登录流程中的审核暴露点

登录页当前仍会处理以下错误提示：

- `account not activated`
- `account pending review`
- `account rejected`
- `account disabled`

如果只隐藏管理后台审核入口，而不处理飞书新用户状态，普通用户仍然会从登录错误中感知审核流。

因此需要一条最小后端策略：

- 飞书授权新用户默认自动审核通过

## 4. 总体方案

### 4.1 前端可见性收口

整体分为三块：

1. 登录页去邮箱化
2. 管理后台去用户审核化
3. 设置页去邮箱权限资格表达

### 4.2 后端最小兜底

虽然本次不做后端结构改造，但需要保证：

- 新飞书用户在主登录链路不会落入前端可见的 `review_pending`

这属于策略修正，不属于认证系统重构。

## 5. 页面级具体改动清单

本节为后续实施的细化清单，按页面和接口列出“移除什么、保留什么、哪些地方要改文案”。

### 5.1 登录页

涉及文件：

- `src/routes/auth/login.tsx`
- `src/copy/auth.ts`

需要移除：

- 邮箱辅助登录入口按钮
- 切换到邮箱登录视图的逻辑
- 邮箱输入框
- 密码输入框
- 邮箱密码提交逻辑
- 与邮箱辅助登录相关的 loading / error / info 状态

需要保留：

- 飞书登录入口
- 飞书客户端内 H5 免登逻辑
- 浏览器飞书 OAuth 跳转逻辑
- 登录成功后的 `/api/v1/users/me` 刷新逻辑
- 登录成功后的 redirect 逻辑

需要改文案：

- 将“飞书授权是主登录方式；邮箱仅作为辅助登录和管理权限绑定方式”改为只表达飞书登录
- 删除“邮箱辅助登录”
- 删除“已绑定邮箱的账号可通过邮箱密码辅助登录”
- 删除与邮箱未绑定、邮箱未激活相关的公开提示
- 如仍保留 `account pending review` 等错误映射，应改写为不显性突出审核流程的用户可见表达；更优方案是通过飞书自动通过避免命中该分支

### 5.2 管理后台

涉及文件：

- `src/routes/management.tsx`
- `src/copy/management.ts`

需要移除：

- `users` tab
- 用户筛选状态相关 UI
- 用户列表渲染逻辑
- 用户详情渲染逻辑
- 审核按钮与状态变更按钮
- 请求 `/api/v1/admin/users`
- 请求 `/api/v1/admin/users/:id`
- 所有与用户审核相关的 React Query key 与 mutation

需要保留：

- 技能管理相关视图
- 技能删除 / 恢复等仍然需要保留的管理动作
- 管理页整体权限判断入口

需要改文案：

- `subtitle` 不能再强调“审核访问权限”
- 去掉 users tab 相关文案
- 去掉审核状态、审核动作、审核引导相关文案
- `emailBindingRequired` 不再保留为面向用户的提示语
- 权限不足统一改为无权限提示，例如“当前账号无权访问管理后台”

实现约束：

- 不是仅隐藏按钮，而是前端彻底不再请求用户审核接口
- 页面默认视图应直接收敛到 skill 管理相关内容

### 5.3 设置页

涉及文件：

- `src/routes/settings.tsx`
- `src/copy/settings.ts`

需要移除：

- 面向用户公开表达“邮箱绑定决定管理权限资格”的文案
- 与邮箱资格叙事相关的提示语

需要保留：

- 基础资料展示
- 飞书绑定状态展示
- API Token 管理能力

需要改文案：

- 删除 `managementLocked`
- 删除 `managementReady`
- 删除“绑定邮箱后，账号才具备获得管理权限的资格”
- 如果仍保留邮箱字段展示，不应再把它描述成权限前提条件

说明：

- 本次需求不强制删除所有邮箱字段展示
- 但不允许继续把邮箱字段当作产品权限逻辑的公开说明

## 6. 接口级影响清单

### 6.1 本次前端必须停止请求的接口

- `GET /api/v1/admin/users`
- `GET /api/v1/admin/users/:id`
- `POST /api/v1/admin/users/:id/approve`
- `POST /api/v1/admin/users/:id/reject`
- `POST /api/v1/admin/users/:id/disable`
- `POST /api/v1/admin/users/:id/enable`

说明：

- 即使某些接口当前只在按钮点击时触发，也应随着用户审核入口移除而一并退出前端主流程

### 6.2 本次允许保留但前端不再暴露的接口

- `POST /auth/register`
- `POST /auth/activate`
- `POST /auth/login`
- 其他与邮箱绑定、重发激活码相关的既有接口

说明：

- 这些接口本次作为兼容层保留
- 不要求前端页面继续提供入口

### 6.3 需要保持稳定的接口

- `POST /auth/feishu/h5-login`
- `GET /auth/feishu`
- `GET /auth/feishu/callback`
- `GET /api/v1/users/me`
- 与技能管理相关的管理接口

## 7. 文案收口清单

### 7.1 必须删除的文案方向

- 邮箱辅助登录
- 邮箱密码登录
- 邮箱未绑定无法获得管理权限
- 邮箱绑定后才能参与管理权限判定
- 管理后台中的用户审核、待审核、通过、拒绝等显性运营语言

### 7.2 必须保留的文案方向

- 飞书是当前登录入口
- 管理后台需要权限
- 设置页可以展示飞书绑定状态和账号基础信息

### 7.3 建议替换的文案方向

- 将“邮箱原因”替换为“权限不足”
- 将“审核流描述”替换为更中性的登录失败提示，或通过后端状态策略避免用户触达

## 8. 测试影响清单

### 8.1 需要调整的前端测试

- `src/__tests__/auth-login-route.test.tsx`
- `src/__tests__/management-route.test.tsx`

### 8.2 重点校验项

- 登录页不再出现邮箱辅助登录入口
- 登录页只保留飞书登录主路径
- 管理页不再请求用户审核接口
- 管理页不再渲染 users 相关 UI
- 管理页权限不足时显示统一无权限提示
- 设置页不再显示邮箱权限资格文案

## 9. 后端最小调整建议

涉及位置：

- `backend/internal/service/auth_service.go`

建议目标：

- 飞书授权新用户默认进入可登录状态
- 让普通用户在飞书主流程中不感知 `review_pending`

说明：

- 本次不要求删除审核字段
- 本次不要求删除审核接口
- 本次不要求重构 `HasManagementAccess` 或 `IsSuperuser`
- 这里只要求对“飞书新用户登录状态”做最小兜底修正

## 10. 非目标与后续空间

本次文档故意不进入以下话题：

- 完整移除邮箱身份体系
- 完整移除审核体系
- 重构超级管理员判定规则
- 基于授权渠道重做权限模型

这些内容属于后续阶段，不纳入本次实现边界。
