# 去邮箱可见性改造需求文档

## 1. 文档目的

本文档用于定义 ClawHub 当前项目中“去掉基于邮箱的用户流程可见性”的需求边界，作为后续技术设计、任务拆解和实施验收的依据。

本文档基于当前仓库代码现状编写，目标不是抽象讨论，而是为现有 Go 后端 + 前端页面提供一轮可落地的收口方案。

## 2. 背景

当前系统虽然已经以飞书授权作为主登录方向，但产品可见层仍然保留了较强的邮箱流程存在感，主要表现在：

- 登录页仍保留邮箱辅助登录入口和邮箱密码表单
- 文案中仍明确表达邮箱是辅助登录与管理权限绑定方式
- 管理后台仍对前端暴露用户审核能力
- 管理后台在无权限时仍向用户暴露“邮箱绑定 required”这类原因
- 设置页仍公开表达“邮箱绑定后才具备管理权限资格”

这些内容会让用户继续感知到一套显性的“邮箱注册 / 激活 / 登录 / 审核”产品流程，与当前产品方向不一致。

## 3. 核心目标

本次需求的核心目标如下：

1. 从前端产品可见性上收起邮箱用户流程
2. 让飞书登录成为用户可见的唯一登录入口
3. 从前端移除用户审核能力的可见性
4. 避免普通用户从登录页、设置页、管理页感知“邮箱资格”与“审核流”叙事
5. 在不删除后端既有能力的前提下，为后续进一步认证重构留出空间

## 4. 范围

### 4.1 本次必须覆盖

- 登录页仅保留飞书登录入口
- 删除邮箱辅助登录 UI 和相关文案
- 管理后台彻底不再请求用户审核接口
- 管理后台不再暴露用户审核能力
- 管理后台 403 提示统一为无权限，不再暴露邮箱原因
- 设置页去掉“邮箱绑定决定管理权限资格”的公开表达
- 飞书授权流程中的新用户默认自动审核通过

### 4.2 本次建议覆盖

- 梳理前端测试中对邮箱登录、邮箱文案、用户审核页面的断言
- 清理与本次产品方向不一致的文案
- 统一管理后台的页面定位，使其不再以“用户审核后台”对外呈现

### 4.3 本次明确不做

- 不删除后端邮箱注册、激活、登录接口
- 不删除后端用户审核接口
- 不删除数据库中的邮箱或审核相关字段
- 不处理存量用户
- 不做 CLI 协议调整
- 不做完整权限模型重构

## 5. 明确边界

本次需求是“去掉当前这套系统的邮箱流程可见性”，不是“彻底移除邮箱体系”。

这里需要明确区分两层：

- 产品可见层：本次要收起
- 后端兼容能力：本次暂时保留

因此，本次实施后可能仍存在以下事实：

- 后端仍保留 `/auth/register`、`/auth/activate`、`/auth/login`
- 后端仍保留用户审核接口
- 数据库中仍保留邮箱和审核状态字段
- 某些权限判断在后端内部仍可能依赖既有逻辑

这些都不属于本次需求的失败，而是刻意保留的兼容层。

## 6. 产品方案

### 6.1 登录入口策略

前端登录页调整为：

- 只保留飞书登录
- 不再向用户展示邮箱辅助登录入口
- 不再展示邮箱密码登录表单

产品语义上应明确为：

- 飞书是唯一显性登录入口
- 邮箱不再作为用户可见流程的一部分

### 6.2 审核可见性策略

前端不再向管理员显性暴露“审核用户”能力：

- 不再展示用户审核 tab
- 不再展示待审核用户列表
- 不再展示 approve / reject / disable / enable 等审核操作入口
- 不再请求用户审核接口

同时，对普通用户也不再显性暴露“等待审核”产品叙事。

为避免用户在飞书主流程中感知审核状态，本次确认：

- 飞书授权流程中的新用户默认自动审核通过

## 7. 影响范围

### 7.1 前端页面

核心影响页面如下：

- `src/routes/auth/login.tsx`
- `src/routes/management.tsx`
- `src/routes/settings.tsx`

### 7.2 前端文案

核心影响文案如下：

- `src/copy/auth.ts`
- `src/copy/management.ts`
- `src/copy/settings.ts`

### 7.3 前端测试

核心影响测试如下：

- `src/__tests__/auth-login-route.test.tsx`
- `src/__tests__/management-route.test.tsx`

### 7.4 后端最小行为调整

后端本次不做结构性删除，但需要确认飞书授权流程的用户状态策略：

- 飞书授权创建的新用户应直接进入可登录状态
- 不让普通用户在飞书主流程中遇到 `review_pending`

## 8. 主要风险

### 8.1 前端隐藏与后端保留并存

本次是“前端收口 + 后端兼容保留”，因此短期内会出现：

- 前端不再暴露某能力
- 后端仍保留该能力

这属于预期结果，但需要在研发认知上保持一致。

### 8.2 权限原因不再显性可见

管理后台改为统一无权限提示后，用户不再知道被拒绝的具体原因。  
这符合产品收口目标，但会减少前端层面的原因透明度。

### 8.3 页面定位变化

管理后台移除用户审核可见性后，页面定位会从“用户审核 + skill 管理”变成更偏向“skill 管理后台”，需要同步调整标题、副标题和默认内容组织。

## 9. 验收标准

本次需求完成后，应满足以下验收结果：

1. 登录页不再出现邮箱辅助登录入口、邮箱密码表单及相关文案。
2. 管理后台前端不再请求 `/api/v1/admin/users` 和 `/api/v1/admin/users/:id`。
3. 管理后台前端不再展示用户审核相关 UI。
4. 管理后台权限不足时，只显示统一无权限提示，不再显示邮箱绑定原因。
5. 设置页不再公开表达“邮箱绑定决定管理权限资格”。
6. 新的飞书授权用户在主登录链路中不会看到“等待审核”提示。
7. 后端既有邮箱接口、审核接口和数据库结构保持兼容保留。
