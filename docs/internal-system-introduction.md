
# ClawHub 项目介绍与内部系统迁移说明

## 一、文档目的

这份文档用于从组织内部视角介绍当前的 `clawhub` 项目，回答四个问题：

1. `clawhub` 目前本身具备什么能力
2. 如果服务组织内部，我们需要的应该是怎样一套系统
3. 为了支撑这个目标，这次迁移具体做了哪些事情
4. 迁移完成后，当前系统与内部需求的契合程度如何

本文重点不是单纯介绍技术栈，而是说明 `clawhub` 从“公开技能仓库”走向“组织内部技能资产平台”的演进逻辑。

## 二、ClawHub 当前是什么

`clawhub` 当前可以理解为一个面向 Agent 技能资产的注册中心与分发平台。它围绕 `SKILL.md` 及配套文本文件，提供技能的发布、版本管理、检索、查看、下载、安装和更新能力。

从使用方式看，它不是单一的 Web 网站，而是一套由 Web 前端、HTTP API、CLI 和共享 schema 共同组成的系统：

- Web 前端负责浏览、搜索、详情查看、上传和导入
- HTTP API 对外提供统一的技能查询、下载、发布和解析接口
- CLI 面向开发者和自动化流程，支持安装、更新、检查和发布
- 共享 schema 保证前后端和 CLI 在请求、响应和数据结构上的一致性

换句话说，`clawhub` 的核心价值不是“展示技能页面”，而是“把技能资产以统一格式沉淀下来，并让人和工具都能稳定消费”。

## 三、ClawHub 当前已经具备的能力

### 3.1 技能资产管理能力

当前系统已经具备比较完整的技能生命周期管理能力：

- 支持基于 `SKILL.md` 和附属文本文件发布 skill
- 支持 skill 的版本化管理，包含版本号、changelog 和历史版本记录
- 支持查看 skill 详情、版本列表和单个文件内容
- 支持软删除与恢复，保证资产治理具备基本回退能力

在这个层面上，`clawhub` 已经不是简单的文件上传工具，而是一个有版本关系、有元数据结构、有状态流转的资产管理系统。

### 3.2 检索与发现能力

系统当前支持两类发现能力：

- 浏览能力：按列表、分页、排序查看技能资产
- 搜索能力：基于 PostgreSQL `ILIKE + pg_trgm` 的模糊搜索，按名称、描述、标签匹配

这意味着系统已经可以承担“内部技能目录”的角色，满足用户快速找到已有能力沉淀的基本需求。虽然当前还不是语义级检索，但在 Phase 1 范围内已经可以覆盖大多数明确目标的查询场景。

### 3.3 分发与消费能力

`clawhub` 的另一个关键能力是分发，而不是只做存储。

当前已经具备：

- `GET /api/v1/download` 提供版本 ZIP 下载
- `GET /api/v1/resolve` 提供基于 hash 的版本解析
- `/.well-known/clawhub.json` 提供 registry 发现
- CLI 支持 `install`、`update`、`inspect`、`explore`、`publish` 等完整流程

这意味着 skill 不只是“被存起来”，而是可以真正进入开发者工作流和自动化流程，被安装、更新、校验和复用。

### 3.4 自托管与基础设施适配能力

项目当前已经具备较强的自托管属性：

- 后端基于 Go + Gin
- 元数据存储基于 PostgreSQL
- 文件存储可接入 OSS / S3 兼容对象存储
- 前端通过 HTTP API 与后端解耦

对组织内部来说，这一点很关键。它意味着系统能够部署在自己的基础设施里，数据、接口和运行方式都可控，不需要依赖特定第三方 BaaS 的运行时能力。

## 四、如果服务组织内部，我们真正需要什么样的系统

如果把 `clawhub` 放到组织内部场景里看，我们需要的不是一个“技能展示站点”，而是一套“技能资产管理与分发底座”。这套系统至少应该覆盖以下几层能力。

在这个前提下，有两个判断需要先明确：

- 我们需要的是集中式管理，而不是依赖各团队本地各自维护
- 我们可以支持从 GitLab 导入，但不能把 GitLab 当成整个系统的唯一载体

这两个判断决定了系统形态，也决定了后续迁移方向。

### 4.0 为什么必须采用集中管理，而不是本地管理

如果 skill 只停留在本地目录、个人仓库或团队私有脚本中，短期内看起来灵活，但从组织角度看会带来几个根本问题。

第一，本地管理天然会造成分散。不同团队会用不同方式组织 skill，命名、版本、元数据和目录结构都可能不一致，最终导致资产无法统一检索，也无法形成公司级知识地图。

第二，本地管理不可发现。一个 skill 即使已经存在，只要没有统一入口，其他团队就很难知道它存在，更难判断它是否可复用、是否仍然有效、当前推荐使用哪个版本。

第三，本地管理不可治理。没有统一的版本记录、删除恢复、发布入口和状态控制，就很难建立正式的变更流程，也无法回答“谁发布的、当前谁在用、出了问题怎么回退”这类组织必然会问的问题。

第四，本地管理难以服务非技术角色。技术同学可以接受本地目录、Git 仓库、命令行和脚本，但当 skill 逐步成为全公司级别的知识沉淀后，使用者不会只包括工程师，还会包括运营、产品、业务、支持等角色。对于这些用户，本地文件组织和 Git 工作流的门槛过高，无法成为普适的知识消费方式。

因此，从组织层面看，skill 一旦被视为正式资产，就必须从“本地文件”升级为“平台化对象”。集中管理的意义并不是限制灵活性，而是让 skill 具备统一入口、统一标准、统一分发和统一治理能力。

### 4.1 资产层：统一沉淀和标准化管理

组织内部首先需要一个统一的技能资产入口，用来解决技能分散、格式不一、版本难追踪的问题。

系统需要能够：

- 统一管理 skill 的元数据、文件和版本
- 明确每个 skill 的唯一标识、当前版本和历史版本
- 支持发布、回滚、删除恢复等基础操作
- 让 skill 成为可治理、可复用、可追踪的正式资产

### 4.2 检索层：让内部知识能够被找到

内部系统的第二个核心要求是“能找到”。如果一个技能已经存在，但团队成员无法快速发现，它的沉淀价值会迅速下降。

因此系统需要：

- 支持按名称、标签、描述和用途检索
- 支持按更新时间、下载量、版本情况等维度浏览
- 后续具备向语义搜索、推荐和相似技能发现扩展的空间

### 4.3 分发层：让技能进入真实工作流

对组织内部来说，技能资产必须能被稳定消费，而不是停留在文档层。

因此系统应该支持：

- 通过统一 API 和 CLI 进行下载、安装和更新
- 支持版本锁定、版本解析和一致性校验
- 支持被脚本、流水线和内部工具链直接调用

只有具备分发能力，系统才是生产底座，而不是内容库。

### 4.4 治理层：满足组织化使用的管理要求

一旦系统进入组织内部使用，治理能力的重要性会迅速上升。相比个人或社区场景，组织更关心的是可控性、边界和责任归属。

因此内部系统最终需要具备：

- 认证和权限控制
- 发布审批或审核机制
- 审计日志和可追溯性
- 删除、恢复、禁用等治理动作
- 配额、限流、健康检查和可观测性

这部分能力并不是为了“功能完整”，而是为了让系统能真正进入团队协作和正式运营环境。

### 4.5 基础设施层：可部署、可运维、可替换

从基础设施角度，组织内部系统通常还要满足：

- 可自托管部署
- 数据可迁移、可备份、可恢复
- 存储与数据库组件可独立替换
- 前后端边界清晰，避免平台绑定过重

这也是为什么我们需要把系统从强耦合的托管后端模型，迁移到更可控的通用后端架构。

### 4.6 为什么 GitLab 可以作为导入来源，但不能作为唯一依赖

GitLab 在组织内部是重要的技术协作基础设施，因此它很适合作为 skill 的来源之一，例如：

- 从已有仓库导入 skill 文件
- 复用现有代码评审流程管理部分技术型 skill
- 让研发团队以熟悉的方式维护底层内容

但 GitLab 不能直接等同于组织内部 skill 平台，原因主要有四个。

第一，GitLab 的核心对象是代码仓库，而不是 skill 资产。它擅长管理源码、分支、提交和 MR，但不天然提供围绕 skill 的统一元数据、版本解析、下载分发、registry discovery 和面向消费侧的检索体验。

第二，GitLab 的使用门槛偏技术化。仓库、分支、提交历史、目录结构和权限模型对研发同学是自然的，但对非技术角色并不友好。既然我们判断 skill 最终会成为全公司级知识沉淀，就不能把主要使用入口建立在只有技术人员熟悉的协作模型上。

第三，GitLab 无法自然承接“消费平台”的职责。我们需要的不只是保存内容，还包括统一搜索、统一安装、统一下载、统一版本解析和后续的审批、审核、统计、推荐等能力。GitLab 可以承载内容源，但很难直接承担这些平台职责。

第四，完全依赖 GitLab 会让 skill 的组织方式被代码仓库结构反向决定。这样会使知识资产继续附着在研发流程之上，而不是上升为公司级共享资产。长期看，这会限制 skill 向跨部门、跨角色、跨场景扩展。

因此，更合理的关系应该是：

- GitLab 是重要的内容来源和导入通道
- `clawhub` 是统一的 skill 注册、检索、分发和治理平台

也就是说，我们不是要脱离 GitLab，而是要避免被 GitLab 定义系统边界。

## 五、围绕内部目标，这次迁移做了哪些事情

本次迁移的核心，不是把技术栈从 A 换成 B，而是把 `clawhub` 从“依赖特定后端平台能力的应用”重构成“可作为内部底座部署和维护的系统”。

### 5.1 后端从 Convex 迁移到 Go + Gin

原有架构中，后端能力较多依赖 Convex 提供的数据、函数和 HTTP 路由模型。迁移后，后端统一落到 `backend/` 目录，采用 Go + Gin 提供独立 HTTP 服务。

这一改造带来的直接变化是：

- 服务端运行方式更标准
- 路由、配置、中间件和业务逻辑可以独立演进
- 更容易接入组织内部已有运维体系
- 不再依赖特定 BaaS 平台的运行时约束

### 5.2 用 PostgreSQL 重建核心数据模型

迁移后的系统以 PostgreSQL 承载核心业务数据，围绕 `skills` 和 `skill_versions` 建立新的模型结构。

这一步的意义在于：

- skill 元数据、版本关系、统计字段可以被结构化管理
- 数据库能力可以被直接查询、备份和迁移
- 后续接权限、审计、评论、审批等组织能力时有稳定的数据基础

同时，系统启用了 `pg_trgm` 扩展，通过 `ILIKE + similarity` 提供模糊搜索，为内部目录型使用场景提供可接受的搜索体验。

### 5.3 用对象存储替代平台内置文件能力

原有系统中的文件存储能力绑定在 Convex 模型内。迁移后，文件上传、下载和删除被抽象为存储服务，并落到 OSS / S3 兼容对象存储。

这一改造完成了两件事：

- 元数据与文件内容彻底解耦
- 文件存储实现具备了可替换性和基础设施适配能力

对组织内部来说，这意味着可以根据合规、成本或网络要求选择自己的对象存储方案。

### 5.4 保持 API 与 CLI 工作流的连续性

为了不破坏现有使用方式，本次迁移保留并实现了 Phase 1 所需的关键 API：

- 搜索、列表、详情、版本历史、单文件查看
- 发布、删除、恢复
- ZIP 下载和版本解析
- registry 发现

这保证了 Web 前端和 CLI 都可以继续围绕统一接口工作。系统对使用者来说仍然是一个 skill registry，只是底层实现从托管平台转成了自有后端。

### 5.5 前端从 Convex 依赖转为标准 HTTP 获取

前端原先依赖 Convex hooks 获取和更新数据。迁移后，数据访问改为 TanStack Query + `fetch('/api/v1/...')`。

这一步的意义不只是“换一个库”，而是：

- 前端不再依赖特定后端 SDK
- 前后端契约更明确
- 更容易做本地联调、环境切换和独立部署
- 后续若继续调整后端实现，前端改动面更可控

## 六、迁移完成后，当前系统具备了什么能力

基于当前仓库状态，可以把迁移后的系统能力总结为以下四点。

### 6.1 已形成完整的技能注册中心基础闭环

当前系统已经具备从发布、存储、查询、查看到下载的完整闭环。对于一个内部 skill registry 的 Phase 1 来说，这已经覆盖了最核心的主路径。

### 6.2 已具备面向组织内部部署的技术基础

当前架构已经具备：

- 独立后端服务
- 独立数据库
- 独立对象存储
- 前后端解耦接口

这使得系统可以作为组织内部的正式服务运行，而不是开发性质的原型应用。

### 6.3 已支持多消费端一致接入

当前系统同时服务：

- Web 浏览与操作
- CLI 安装与发布
- 后续内部自动化工具或脚本

这说明系统的能力输出已经不是页面级，而是平台级。

### 6.4 已为后续治理能力预留了演进空间

虽然 Phase 1 明确不实现认证、审核、评论、星标、管理后台等能力，但当前的 Go 后端 + PostgreSQL 架构已经为这些功能保留了清晰的扩展路径。

这意味着当前系统虽然还不是最终形态，但技术方向已经对了。

### 6.5 已具备从“技术工具”走向“组织平台”的基础条件

从当前架构和能力边界看，`clawhub` 已经不再局限于服务研发同学的命令行工具链，而是具备继续演化成组织级平台的基础条件。

具体来说：

- Web 入口使非技术用户具备浏览和理解 skill 的可能
- 标准化 API 让系统可以被其他内部产品和流程接入
- 集中式元数据和版本体系让 skill 可以被当作正式知识资产管理

这点很重要，因为它决定了系统未来不是“工程师内部的小工具”，而是“面向全员知识沉淀与能力复用的平台底座”。

## 七、当前系统与组织内部需求的契合度评估

如果把“组织内部技能资产平台”的目标拆开来看，当前系统与需求的契合程度可以分为三个层次。

### 7.1 高契合部分

以下部分已经与内部需求高度匹配：

- skill 资产的统一建模和版本管理
- 基于 Web 和 CLI 的统一分发方式
- HTTP API 形式的标准化能力输出
- PostgreSQL + 对象存储的自托管基础设施形态
- 基于模糊匹配的基础搜索能力

这些能力已经足够支撑一个内部技能仓库在初期投入使用。

### 7.2 中等契合部分

以下部分已经有基础，但还不是组织级最优形态：

- 搜索：当前更偏关键词和模糊匹配，后续可以补充语义搜索和推荐
- 统计：已有基础字段，但还缺少更完整的使用分析和运营视图
- 前端体验：已经能完成主流程，但还可以进一步围绕内部使用场景优化信息结构和操作路径

这些不是缺失，而是“可用但还不够强”。

### 7.3 低契合或待补齐部分

以下部分是系统要真正进入组织化运营时必须补齐的能力：

- 认证与权限体系
- 发布审核、禁用和审批流
- 审计日志与操作追踪
- 团队、租户或更细粒度的隔离能力
- 更完善的可观测性、告警和运维工具

这部分能力决定系统能否从“内部可试用”走向“内部可治理、可长期运营”。

## 八、文档中还建议补充的两个视角

除了上面的主线，如果后续这份文档要用于更正式的内部沟通，我建议再补充两个视角。

### 8.1 组织收益视角

可以明确写出系统上线后对组织的直接收益，例如：

- 减少重复建设，提升已有 skill 的复用率
- 降低 skill 的查找成本、学习成本和接入成本
- 让零散经验从个人或小团队资产升级为公司共享资产
- 为后续 AI 助手、内部自动化平台和知识检索系统提供统一技能底座

这部分有助于让非技术管理者快速理解项目价值。

### 8.2 演进边界视角

可以增加一段说明当前阶段“已经解决什么、刻意没有解决什么”。

例如：

- 当前阶段重点解决统一管理、统一检索、统一分发
- 当前阶段暂不解决复杂权限、多租户、深度审批和智能推荐
- 后续阶段再补治理与智能化能力

这样可以避免读者对当前系统产生“为什么还没有全部能力”的误解。

## 九、结论

综合来看，`clawhub` 当前已经不只是一个技能展示网站，而是一套具备技能资产管理、检索、分发和自托管能力的基础平台。

这次迁移的真正价值，在于把系统从依赖托管后端的平台形态，转成了一个更适合组织内部部署、运维和扩展的标准化系统。迁移后的架构已经能够支撑“内部技能仓库”的核心诉求，并且为后续补齐权限、治理和智能检索能力打下了基础。

如果以“组织内部技能资产底座”作为目标，当前系统已经达到了“主流程可用、架构方向正确、可以继续迭代扩展”的阶段。后续工作的重点，不再是重新定义系统，而是沿着治理、权限和智能化三个方向继续补全。
